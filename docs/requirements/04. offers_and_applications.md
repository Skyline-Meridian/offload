# 04. Offers, Applications and Messaging

---

## 1. Offers

An offer is an opportunity an organisation publishes for players: a playing contract, trial, scholarship, coaching role or brand partnership. Offers from all organisation types, brands included, have the same fields. Any extra details go in the description.

### 1.1 Offer fields

| Field | Type | Required | Rule |
|---|---|---|---|
| Title | text | yes | Maximum 150 characters. |
| Description | formatted text | yes | Maximum 5,000 characters. |
| Paid or unpaid | Paid / Unpaid | yes | |
| Positions | one or more from the positions list (`02`) | no | |
| Required skills | one or more from the game and soft skills lists (`02`) | no | |
| Location | one-line address | no | Defaults to the organisation's address. Shown on a map. |
| Organisation | the manager's organisation | system | Not editable. |
| Offered by | Club, Union, College/University or Brand | system | Taken from the organisation. |
| Status | Published, Closed, Expired | system | |
| Published on | date | system | |
| Expiry date | date | system | Always 30 days after the publishing date. Not chosen or edited by the manager. |

### 1.2 Creating and managing offers

**OFF-1.1** THE System SHALL let a verified manager whose organisation has an active subscription create, edit, close, copy and delete that organisation's offers.

**OFF-1.2** WHILE the organisation has no active subscription, THE System SHALL block creating, editing, closing, copying and deleting offers, and SHALL show an upgrade message.

**OFF-1.3** WHILE the organisation has no active subscription, THE System SHALL keep its published offers visible to players until their expiry date.

**OFF-1.4** WHEN an offer is published, THE System SHALL set its expiry date to 30 days after the publishing date. Editing the offer SHALL not change the expiry date.

**OFF-1.5** WHEN an offer reaches its expiry date, THE System SHALL mark it Expired, remove it from the offers directory and stop new applications.

**OFF-1.6** THE System SHALL give managers a section to manage their organisation and its offers. It SHALL list all the organisation's offers, Published, Closed and Expired, with their status, expiry date and number of applications. Expired and Closed offers stay visible there to the organisation's managers only.

**OFF-1.7** WHEN an offer is created, THE System SHALL fill in the organisation, "offered by", the expiry date and the default location from the manager's organisation.

**OFF-1.8** IF the title, description or paid/unpaid choice is missing, THEN THE System SHALL reject the offer with a message.

**OFF-1.9** Only managers SHALL create offers. Staff SHALL not create offers on behalf of an organisation.

**OFF-1.10** Managers SHALL edit only Published offers. A Closed or Expired offer cannot be edited, reopened or republished.

**OFF-1.11** THE System SHALL let a manager close a Published offer at any time. A Closed offer leaves the offers directory and stops new applications, like an Expired one.

**OFF-1.12** THE System SHALL let a manager delete an offer only while it has no applications. An offer with applications can only be closed, so players keep their application history.

**OFF-1.13** THE System SHALL offer a "Copy as new offer" action on Closed and Expired offers. WHEN a manager uses it, THE System SHALL open a new offer with the old offer's fields filled in. WHEN the manager publishes it, it becomes a separate offer with its own publishing date, a new 30-day expiry and no applications. The old offer stays Closed or Expired with its own applications. Players who applied to the old offer can apply to the new one.

### 1.3 Offers directory and offer page

**OFF-2.1** Offers directory and offer pages SHALL require login. Visitors see "You need to be logged in". No subscription is needed to view offers.

**OFF-2.2** THE directory SHALL list Published offers that have not expired, newest first, in pages.

**OFF-2.3** THE directory SHALL provide these filters, which can be combined:

| Filter | Type |
|---|---|
| Search | Title and description |
| Date | Published date range |
| Positions | Several positions; matches offers with any of them |
| Required skills | Several skills; matches offers with any of them |
| Organisation | One organisation |
| Paid | Paid / Unpaid |

**OFF-2.4** THE offer page SHALL show title, organisation (with link and logo), offered by, paid or unpaid, positions, required skills, location with map, expiry date and description.

**OFF-2.5** THE System SHALL show an organisation's open offers on its organisation page and in the managers' section (OFF-1.6).

**OFF-2.6** THE offer page SHALL show the "Apply" button to verified players. WHERE the player has already applied, THE page SHALL show "Applied" and the application status instead.

## 2. Applications

### 2.1 Application fields

| Field | Type | Rule |
|---|---|---|
| Offer | the offer | |
| Player | the applicant | |
| Note | text | Optional. Maximum 2,000 characters. |
| Status | Submitted, Shortlisted, Contacted, Rejected, Withdrawn | See APP-1.6. |
| Applied on | date | |

### 2.2 Rules

**APP-1.1** WHEN a verified player applies to an open offer, THE System SHALL save the application with status Submitted and notify the organisation's managers by email and in the app. WHILE the organisation has no active subscription, the notification SHALL still be sent, with a "Subscribe to view" link instead of the applicant's details.

**APP-1.2** THE System SHALL allow one application per player per offer. A second attempt SHALL show "You have already applied", unless the earlier application was withdrawn (APP-1.9).

**APP-1.3** IF the offer is closed or expired, or the player is not verified, THEN THE System SHALL refuse the application with a message.

**APP-1.4** Applying SHALL never require a subscription.

**APP-1.5** WHERE the organisation has an active subscription, THE System SHALL show its managers the applications to its offers: player name and photo, primary position, current club, date, note, status and a link to the profile. WHILE the organisation has no active subscription, THE System SHALL not show the applications and SHALL show "Subscribe to view applications".

**APP-1.6** THE System SHALL let a manager with an active subscription change an application's status to Shortlisted, Contacted or Rejected, by hand. No status changes automatically, for example when a manager messages the applicant. Only the player can set Withdrawn (APP-1.9).

**APP-1.7** WHEN an application's status changes, THE System SHALL notify the player by email and in the app. The player sees the current status.

**APP-1.8** THE System SHALL show players a list of their applications with offer, organisation, date and status.

**APP-1.9** THE System SHALL let a player withdraw an application at any time, whatever its status. Its status becomes Withdrawn. WHILE the offer is still open, the player can apply again; the application then returns to Submitted and the managers are notified as for a new application.

**APP-1.10** Managers without an active subscription SHALL not open applicants' profiles. The players directory rule applies (`02` PLR-8.2).

## 3. Messaging

### 3.1 Who can message whom

| From | To | Allowed |
|---|---|---|
| Verified player | Verified player | yes |
| Verified player | Organisation | yes |
| Verified manager | Verified player | yes |
| Verified manager | Another organisation | yes |
| Anyone not verified | Anyone | no |

A message to an organisation is addressed to the organisation, not to a person.

### 3.2 Rules

**MSG-1.1** THE System SHALL show the "Message" button on player profiles and organisation pages only to verified users.

**MSG-1.2** Messaging SHALL never require a subscription.

**MSG-1.3** WHEN a user sends a message to a player, THE System SHALL deliver it to that player.

**MSG-1.4** WHEN a user sends a message to an organisation, THE System SHALL deliver it to the organisation inbox. Every manager of the organisation can open the organisation inbox, and every verified manager receives a copy of each new message (`03` ORG-1.4). A manager therefore has two inboxes: a personal inbox and the organisation inbox.

**MSG-1.5** WHEN a manager replies or writes from the organisation inbox, THE System SHALL show the message as sent by the organisation, with the name of the manager who wrote it. All managers see the full conversation, including replies written by other managers.

**MSG-1.6** THE System SHALL show messages as conversation threads between two parties (user and user, or user and organisation). The inbox SHALL list the conversations, newest activity first, each with the other party's name and photo or logo, a preview of the last message, its date and an unread marker. Opening a conversation SHALL show the whole thread, messages sent and received in date order, with a reply box. There is no separate "sent" view.

**MSG-1.7** IF a message is empty or longer than 2,000 characters, THEN THE System SHALL reject it.

**MSG-1.8** WHEN a message arrives, THE System SHALL notify the recipient in the app and by email. The email SHALL not contain the sender's contact details.

**MSG-1.9** THE System SHALL mark messages as read when the recipient opens the conversation.

**MSG-1.13** Messaging SHALL work as a real-time chat. WHILE a user has the platform open, THE System SHALL show a new message in the open thread, move the conversation to the top of the inbox list and update the unread counts within 2 seconds, without the user reloading the page. A message the user sends SHALL appear in the thread at once.

**MSG-1.14** WHEN the connection is lost, THE System SHALL show that messages are not being updated, reconnect by itself, and then show any messages that arrived in the meantime.

**MSG-1.15** WHEN the recipient is viewing the conversation as a new message arrives, THE System SHALL not send the email notification for that message (MSG-1.8).

**MSG-1.10** THE System SHALL limit how many messages a user can send per hour.

**MSG-1.11** THE System SHALL not provide blocking or reporting of users or messages. Users report problems to staff through the contact form or by contacting an Offload admin directly.

**MSG-1.12** WHEN a user deletes their account, THE System SHALL keep their messages and show the sender as "Deleted user".

## 4. Notifications

**NOT-1.1** THE System SHALL notify:

| Event | Recipient |
|---|---|
| New application | The organisation's managers |
| Application status changed | The player |
| New message | The recipient |
| Offer expires in 3 days | The organisation's managers |
| Offer expired | The organisation's managers |
