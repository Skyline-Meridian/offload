## 1. Purpose

Offload is a rugby recruitment platform for **female rugby players**. Its message is "No agent. No politics. Just your game." Players create a free profile. Clubs, unions, colleges/universities and brands find players, contact them and publish offers. Organisations pay a monthly or yearly subscription.

## 2. Glossary

- **Player**: a rugby player with a profile. Free account.
- **Organisation**: a Club, Union, College/University or Brand.
- **Manager**: a user who administers an organisation on its behalf.
- **Organisation page**: the public page of one organisation.
- **Offer**: an opportunity published by an organisation, such as a playing contract, trial, scholarship or partnership.
- **Application**: a player's response to an offer.
- **Email verification**: the user proved they control their email address.
- **Document verification**: staff checked the user's identity document and approved the account.
- **Verified user**: a user whose email is verified and whose document verification is approved.
- **Subscription**: the paid plan of an organisation.
- **Active subscription**: a subscription that currently grants access (see `06`).
- **League**: a competition a club or union plays in, for example "Premiership (England)".
- **Level**: a free-text description of a club's or union's competition level, for example "Elite 1".
- **EQP**: English Qualified Player.
- **JIFF**: Joueurs Issus des Filières de Formation.
- **Staff**: Offload employees (Offload Admins and Administrators).
- **Dashboard**: the signed-in area of the platform. Every signed-in user has one; its sections depend on the user's role (`05`).

## 3. User roles

| Role | Description |
|---|---|
| Player | Manages own profile. Applies to offers. Messages players and organisations. Free. |
| Manager | Manages one organisation. The organisation's type (Club, Union, College/University or Brand) decides which fields, plans and pages apply. |
| Offload Admin | Staff. Verifies users and organisations, manages content, sees statistics. |
| Administrator | Staff with full access, including settings, plans and roles. |

In the interface a manager is described by the organisation type, for example "Club Manager" or "Brand Manager".

**GEN-1.1** THE System SHALL support the roles above.

**GEN-1.2** THE System SHALL give each user exactly one role.

**GEN-1.3** THE System SHALL link each manager to exactly one organisation, of the type the manager chose.

**GEN-1.4** THE System SHALL enforce every access rule on the server. Hiding a control in the interface SHALL never be the only protection.

## 4. Registration

**GEN-2.1** THE System SHALL provide one registration page with a required choice "Registering as": Player, Club Manager, Union Manager, College / University Manager, Brand Manager.

**GEN-2.2** THE registration form SHALL collect for every role:

| Field | Required | Rule |
|---|---|---|
| First name | yes | |
| Last name | yes | |
| Email | yes | Valid format. Unique, compared case-insensitively. Used to sign in. |
| Password and confirm password | yes | Must match. 8 to 50 characters, with at least one uppercase letter, one lowercase letter, one number and one symbol. |
| Date of birth | yes | In the past. |
| Nationality | yes | From the country list (`02`, section 9). |
| Accept terms and conditions | yes | Must be ticked. The acceptance time and terms version are recorded. |
| Newsletter sign-up | no | If ticked, the user is added to the newsletter list. |

**GEN-2.3** WHILE the user types a password, THE registration form SHALL show which password rules are met.

**GEN-2.4** WHEN the role is Player, THE registration form SHALL also offer the optional player fields: height, weight, strengths, work-ons, colour personality, highlight video, eligible countries, contract end date, current club, capped details, positions, soft skills and club history. All other player fields are completed later in the profile editor.

**GEN-2.5** WHEN the role is a manager, THE registration form SHALL ask the user either to select an existing organisation of the chosen type or to register a new one.

**GEN-2.6** WHEN a manager selects an existing organisation, THE System SHALL record a claim on that organisation. The manager SHALL gain rights over the organisation only after staff approve the claim.

**GEN-2.7** WHEN a manager registers a new organisation, THE System SHALL collect the organisation details defined in `03` and create the organisation as pending.

**GEN-2.8** WHEN registration succeeds, THE System SHALL send a verification email and show a "Check your email" page that tells the user to open the link in the email.

**GEN-2.9** IF registration fails, THEN THE System SHALL show a message next to the field concerned. Required messages: email already registered, password rules not met, passwords do not match, required field missing, already signed in.

**GEN-2.10** THE System SHALL protect registration against automated sign-ups.

## 5. Email verification

**GEN-3.1** WHEN a user registers, THE System SHALL send an email containing a verification link that can be used once and expires.

**GEN-3.2** WHEN the user opens a valid link, THE System SHALL mark the email as verified and show a success page.

**GEN-3.3** IF the link is invalid, expired or already used, THEN THE System SHALL show a failure page with a "send a new link" action.

**GEN-3.4** THE System SHALL let a signed-in user with an unverified email request a new link, limited to a few requests per hour.

**GEN-3.5** THE System SHALL let a user with an unverified email sign in. The email can be verified at any later time.

**GEN-3.6** WHILE a user's email is unverified, THE System SHALL show a "Verify your email" prompt on their dashboard.

**GEN-3.7** WHILE a user's email is unverified, THE System SHALL not allow the user to submit documents for review, appear in any directory, send messages or apply to offers.

**GEN-3.8** An account is "unverified" WHILE both its email and its identity document are unverified. This applies to every role, including managers.

**GEN-3.9** WHEN an account has been unverified for 150 days and for 173 days, THE System SHALL email the user a reminder that the account will be deleted in 30 days and in 7 days, with a link to verify the email.

**GEN-3.10** WHEN an account has been unverified for 180 days, THE System SHALL delete the account and its data.

**GEN-3.11** WHEN an unverified manager is deleted, THE System SHALL also delete the organisation they registered IF that organisation is not published. A published organisation SHALL be kept; a new manager can claim it at registration (GEN-2.6).

**GEN-3.12** WHEN a user with an unverified email signs in, THE System SHALL ask them to verify their email, every time they sign in, with a "send a new link" action. The user can close the prompt and continue.

## 6. Sign-in, sign-out, password reset

**GEN-4.1** THE System SHALL sign users in with email and password, and sign them out on request.

**GEN-4.2** IF sign-in fails, THEN THE System SHALL show one generic message that does not reveal whether the account exists.

**GEN-4.3** WHEN sign-in fails repeatedly for one account, THE System SHALL lock sign-in for that account for a period and tell the user.

**GEN-4.4** THE System SHALL provide "Forgot password" and "Reset password" pages. The user identifies the account by email. The reset link SHALL be usable once and expire. The new password follows the rules in GEN-2.2.

**GEN-4.5** WHEN a password is reset, THE System SHALL sign the user out on other devices.

**GEN-4.6** THE System SHALL keep every user, including staff, signed in for 1 year after their last visit. Each visit moves the expiry forward. The session ends earlier only when the user signs out, resets the password, or is suspended.

**GEN-4.7** THE System SHALL let a user sign out of all devices from their account settings.

## 7. Verification model

1. The user registers. Email and document are unverified.
2. The user verifies their email.
3. The user uploads an identity document. A manager who registers a new organisation also uploads an organisation document.
4. Staff review the documents and approve or reject (see `05`). Approving an organisation publishes it.

**GEN-5.1** THE System SHALL track email verification and document verification separately, with the date and, for documents, the staff member who decided.

**GEN-5.2** THE System SHALL let staff revoke a verification.

**GEN-5.3** WHILE a user's document verification is pending, THE System SHALL show "Your account verification is pending approval. Please upload your identification documents and keep your profile up to date."

**GEN-5.4** WHEN a verification is approved or rejected, THE System SHALL notify the user by email and in the app. A rejection SHALL include the reason.

**GEN-5.5** Only verified users SHALL be able to send messages or apply to offers. Staff can always send messages (`05` ADM-4.8). Only verified players SHALL appear in the players directory. Only published organisations SHALL appear in organisation directories.

## 8. Pages and access

**GEN-6.1** THE System SHALL provide these areas with these access rules:

| Area | Visitor (not signed in) | Signed in |
|---|---|---|
| Home, About, Pricing, Contact | Visible | Visible |
| Terms and Conditions, Privacy Policy, Refund Policy | Visible | Visible |
| Register, Login, Forgot password, Email verification result | Visible | Visible |
| Single organisation page (club, union, college/university, brand) | Visible | Visible |
| Organisation directories with search and filters | "You need to be logged in" | Visible |
| Offers directory and single offer page | "You need to be logged in" | Visible |
| Players directory and single player profile | "You need to be logged in" | Verified players and staff: visible. Players who are not verified: a message saying what is missing for verification. Managers: visible only with an active subscription, otherwise "You need to be subscribed to view and access the players database" with a link to the plans. |
| Dashboard | Redirect to login | Every signed-in user; the sections shown depend on the role (`05`), including the staff sections for staff |
| Messages (inbox, sent) | Redirect to login | Own messages |
| Subscription page | Redirect to login | Managers |

**GEN-6.2** WHEN a visitor opens a page that requires login, THE System SHALL show "You need to be logged in" with a login button, and return the user to that page after login.

**GEN-6.3** THE System SHALL provide a search for signed-in users across clubs, unions, colleges/universities, brands and offers.

**GEN-6.4** THE home page SHALL contain: an introduction ("What is Offload?"), a "Build your free player profile" call to action, a sponsors strip, a "Why choose Offload" section with blocks for players, clubs/unions and universities/colleges, a benefits list per audience, testimonials and a league table section (England, France, Belgium, New Zealand).

**GEN-6.5** THE league table SHALL be static content, updated once per season. Who updates it is decided in `05` (ADM-13.3).

**GEN-6.6** THE dashboard SHALL show sections relevant to the user's role only. For example, physical testing, caps and club history appear for players only. Brand managers see their brand instead of a club.

## 9. Notifications and email

**GEN-7.1** THE System SHALL send an email for: email verification, password reset, new message received, new application received (to the organisation), application status change (to the player), verification approved or rejected, and the billing events in `06`.

**GEN-7.2** THE System SHALL show an in-app notification for the same events, with an unread count.

**GEN-7.3** THE System SHALL let users mark notifications as read.

**GEN-7.4** THE System SHALL send every notification email in GEN-7.1 to every user. Users cannot turn them off.

**GEN-7.5** THE System SHALL add users who opted in to the newsletter to the newsletter mailing list, and SHALL let them unsubscribe at any time. The newsletter is separate from notification emails.

**GEN-7.6** IF an email cannot be sent, THEN THE System SHALL tell the user and let them retry where the email is needed to continue (verification, password reset).

## 10. Files and media

**GEN-8.1** THE System SHALL accept these uploads:

| Upload | Who | Formats | Max size |
|---|---|---|---|
| Profile picture | All users | JPEG, PNG, WebP, HEIC, AVIF | 2 MB |
| Organisation logo | Managers | JPEG, PNG, WebP, HEIC, AVIF | 2 MB |
| Coach image | Managers | JPEG, PNG, WebP, HEIC, AVIF | 2 MB |
| Identity document | All users | PDF, JPEG, PNG, WebP, HEIC, AVIF | 10 MB |
| Organisation document | Managers | PDF, JPEG, PNG, WebP, HEIC, AVIF | 10 MB |
| CV / résumé | Players | PDF | 10 MB |

**GEN-8.2** IF an upload has a wrong format or is too large, THEN THE System SHALL reject it with a message naming the accepted formats and the limit.

**GEN-8.3** THE System SHALL treat identity and organisation documents as private: only the owner and staff can open them, never through a public link.

**GEN-8.4** THE System SHALL display images in sizes suited to cards, avatars and profile headers.

**GEN-8.5** WHEN an image is uploaded (any of the image formats above, including images uploaded as documents), THE System SHALL convert it to WebP on the server. Users and staff SHALL only ever be shown the WebP version. THE System SHALL delete the original image after the conversion.

**GEN-8.6** SVG files SHALL not be accepted in the first release.

## 11. Privacy and data protection

**GEN-9.1** THE System SHALL comply with UK GDPR and EU GDPR. Users are global.

**GEN-9.2** THE System SHALL let a user download their personal data and delete their account. The last verified manager of an organisation cannot delete their account (see `03` ORG-1.8).

**GEN-9.3** WHEN a user deletes their account, THE System SHALL remove or anonymise their personal data and files, except data that must be kept by law (billing records).

**GEN-9.4** THE System SHALL ask for cookie consent where non-essential cookies are used.

**GEN-9.5** THE System SHALL never show a user's email, phone, date of birth, identity document or billing details to other users, unless the field is defined as public contact data (organisation official email and phone).

**GEN-9.6** THE System SHALL allow players under 18 to register and SHALL treat them the same as adult players.

**GEN-9.7** THE System SHALL not set a minimum registration age and SHALL not ask for parental consent in the first release. Both may be introduced later.

## 12. Quality requirements

**GEN-10.1 Security**: HTTPS only. Sign-in, registration, password reset and messaging are rate-limited. Staff actions are recorded in an audit log. Passwords are never stored or shown in readable form.

**GEN-10.2 Performance**: directory pages and filters respond within 2 seconds at 5,000 players and 500 organisations. Other pages respond within 1 second for 95% of requests.

**GEN-10.3 Accessibility**: public pages meet WCAG 2.1 level AA.

**GEN-10.4 Devices**: all pages work on mobile phones, tablets and desktop browsers (current Chrome, Safari, Firefox, Edge).

**GEN-10.5 SEO**: public pages (home, about, pricing, organisation pages) have titles, descriptions and a sitemap. Login-gated pages are excluded from search engines.

**GEN-10.6 Availability**: 99.5% monthly.

**GEN-10.7 Backups**: data is backed up daily and can be restored to any point in the last 7 days.

**GEN-10.8 Monitoring**: staff are alerted when payments or emails fail repeatedly.

**GEN-10.9 Language**: the first release is in English only (UK spelling). Dates are shown as DD/MM/YYYY.

## 13. Later releases

Not part of the first release. Recorded here so the first release does not block them.

**Languages**
- **GEN-11.1** THE System SHALL add French, Spanish and Japanese after launch.
- **GEN-11.2** THE System SHALL choose the first language from the browser's language, with English as the fallback.
- **GEN-11.3** THE System SHALL save a signed-in user's language on their account and send emails in that language.
- **GEN-11.4** THE System SHALL translate the entire website automatically with Google Translate, including content written by users (bios, organisation descriptions, offers, messages).
- **GEN-11.5** THE System SHALL show dates and numbers in the format of the active language (en-GB, fr-FR, es-ES, ja-JP).
- **GEN-11.6** THE System SHALL mark every automatically translated page "Auto translated", with a "Show original" link to the English version.

**Upload formats**
- **GEN-12.1** THE System MAY accept SVG images in a later release.

**Age rules**
- **GEN-12.2** A minimum age or parental consent MAY be introduced later (see GEN-9.7).
