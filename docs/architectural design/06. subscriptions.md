# 06. Subscription and Billing Design

Implements `docs/requirements/06. subscriptions.md`. Shared parts (viewer, policies, outbox, scheduled jobs, audit, caching) are in `01. general_design.md`. Staff permissions are in `05. admin_section.md` section 4.1.

---

## 1. Approach

- **Stripe owns money movement:**
  - Stripe Billing handles recurring charges, invoices, retries and card updates.
  - Stripe Checkout is the payment page for every purchase.
  - The Stripe Customer Portal is used for payment method, billing details and invoices.
- **The platform owns access:**
  - A local copy of every subscription is kept in step by webhooks.
  - Access checks read only the local tables and never call Stripe during a page request.
- **Trials given by staff are local only.** They need no payment method, so no Stripe object exists for them (SUB-2.2).
- **One Stripe API version is pinned** in code and in the webhook endpoint settings. Upgrading it is a deliberate change.

| Alternative | Why not chosen |
|---|---|
| Own renewal logic charging saved cards | Retries, strong customer authentication (3-D Secure), receipts and failed-payment handling would all have to be built and maintained |
| Stripe Elements with an own payment page | More UI and compliance work; Checkout already provides discount codes, Apple Pay, Google Pay, billing address and phone collection |
| Trials as Stripe subscriptions without a payment method | Possible, but adds Stripe objects for organisations that may never pay, and Stripe would need special settings to end them without charging. A local row is simpler. |

## 2. Stripe objects

| Platform concept | Stripe object |
|---|---|
| Plan (8 at launch) | One Product per plan, with one active Price. A price change creates a new Price on the same Product (section 8). |
| Organisation billing account | One Customer per organisation, never per manager, with `metadata.organisationId` |
| Paid subscription | Subscription with one item, with `metadata.organisationId` and `metadata.planId` |
| Discount code | Coupon (percent off, duration, plans) plus one Promotion Code (the code, expiry, maximum uses) |
| Plan switch at period end | Subscription Schedule with two phases (section 5.5) |
| Payment and receipt | Invoice and its payment |
| Refund | Refund on the invoice's payment |

- **Product per plan:** a Coupon can be limited to Products only, not to single Prices. One Product per plan lets a discount code apply to, for example, Clubs Annual only (SUB-5.2).
- **Customer per organisation:** any manager can manage billing (SUB-3.5), and a manager leaving does not orphan the subscription. The Customer is created the first time a manager opens Checkout, and its email is the billing email collected there.
- **Stripe settings:**
  - Stripe Tax off, no tax rates, no tax id collection (SUB-4.6).
  - Stripe's own customer emails off (receipts, failed payments, trial reminders, renewal reminders), because the platform sends them to every manager (section 10).
  - Smart Retries on, with the retry window and final action in section 5.4.

## 3. Local data model

The standard columns (`createdAt`, `updatedAt`, `createdById`, `updatedById`) and `@db.Uuid` on foreign keys follow the conventions in `01` design section 4 and are left out below. `WebhookEvent` and `BillingReminder` are append-only, so they have `createdAt` and `createdById` only. For refunds, plan prices and discount codes, `createdById` is the staff member who made them.

```prisma
model Plan {
  id               String           @id @default(uuid(7)) @db.Uuid
  name             String           // "Clubs Monthly"
  organisationType OrganisationType
  interval         BillingInterval  // MONTH | YEAR
  stripeProductId  String           @unique
  currentPriceId   String?          @unique   // PlanPrice.id of the price new buyers get
  isActive         Boolean          @default(true)  // false = retired, not sold
  sortOrder        Int
  prices           PlanPrice[]
}

model PlanPrice {
  id            String   @id @default(uuid(7)) @db.Uuid
  planId        String
  stripePriceId String   @unique
  amountPence   Int      // GBP only
}

model BillingAccount {
  organisationId   String   @id
  stripeCustomerId String   @unique
  billingName      String?
  company          String?
  email            String?
  phone            String?
  address          Json?    // line1, line2, city, postcode, country
  cardBrand        String?  // brand and last 4 digits only (SUB-7.1)
  cardLast4        String?
}

model Subscription {
  id                     String             @id @default(uuid(7)) @db.Uuid
  organisationId         String
  kind                   SubscriptionKind   // PAID | TRIAL
  status                 SubscriptionStatus // TRIALING | ACTIVE | PAST_DUE | PAUSED | ENDED
  planId                 String
  planPriceId            String?            // PAID only: the price this subscriber pays
  stripeSubscriptionId   String?            @unique
  purchasedById          String?            // manager who bought it, or staff who gave the trial
  startedAt              DateTime
  currentPeriodStart     DateTime?
  currentPeriodEnd       DateTime?          // next renewal date, or trial end
  isCancelledAtPeriodEnd      Boolean            @default(false)
  scheduledPlanId        String?            // plan switch waiting for the next period
  stripeScheduleId       String?
  discountCodeId         String?
  pastDueSince           DateTime?
  pausedAt               DateTime?
  pausedRemainingSeconds Int?
  accessEndedAt          DateTime?          // when access stopped; start of SUB-6.10 reminders
  endedReason            EndedReason?       // CANCELLED | NON_PAYMENT | TRIAL_ENDED | STAFF

  @@index([organisationId, status])
}

model Payment {
  id                  String        @id @default(uuid(7)) @db.Uuid
  organisationId      String
  subscriptionId      String
  stripeInvoiceId     String        @unique
  invoiceNumber       String?
  status              PaymentStatus // PAID | FAILED | OPEN | VOID
  amountPence         Int           // charged after discount
  discountPence       Int           @default(0)
  amountRefundedPence Int           @default(0)
  failedAttempts      Int           @default(0)
  lastFailureMessage  String?       // the card issuer's reason, shown to staff and managers
  periodStart         DateTime
  periodEnd           DateTime
  paidAt              DateTime?
}

model Refund {
  id             String   @id @default(uuid(7)) @db.Uuid
  paymentId      String
  stripeRefundId String   @unique
  amountPence    Int
  reason         String
}

model DiscountCode {
  id                    String           @id @default(uuid(7)) @db.Uuid
  code                  String           // stored upper-case
  percentOff            Int              // 1 to 100
  plans                 DiscountCodePlan[] // none = every plan
  duration              DiscountDuration // ONCE | REPEATING | FOREVER
  durationMonths        Int?
  expiresAt             DateTime?
  maxRedemptions        Int?
  timesRedeemed         Int              @default(0)
  stripeCouponId        String
  stripePromotionCodeId String           @unique
  isActive              Boolean          @default(true)
}

model DiscountCodePlan {
  discountCodeId String
  planId         String

  @@id([discountCodeId, planId])
}

model WebhookEvent {
  id          String    @id      // Stripe event id
  type        String    // createdAt = when it was received
  processedAt DateTime?
  error       String?
}

model BillingReminder {
  subscriptionId String
  kind           String   // TRIAL_7, TRIAL_1, RENEWAL_14, RENEWAL_7, RENEWAL_1, AGAIN_1, AGAIN_2, AGAIN_7, AGAIN_30, AGAIN_180; createdAt = when it was sent

  @@id([subscriptionId, kind])
}
```

- **One active subscription (SUB-4.5):** two partial unique indexes on `Subscription(organisationId)`:
  - `kind = 'PAID' AND status <> 'ENDED'`
  - `kind = 'TRIAL' AND status <> 'ENDED'`

  A paid subscription bought during a trial can exist next to that trial, because it only starts when the trial ends (SUB-2.5).
- **Locking:** every billing change for an organisation first locks its `BillingAccount` row (or the `Organisation` row before a Customer exists), so webhooks, staff actions and manager actions do not interleave.
- **Status shown to people (SUB-7.1):**

| Shown | Condition |
|---|---|
| Trial | `TRIAL`, or `PAID` with status `TRIALING` |
| Active | `ACTIVE` and not `isCancelledAtPeriodEnd` |
| Cancelled | `isCancelledAtPeriodEnd`, access until `currentPeriodEnd` |
| Past due | `PAST_DUE` |
| Paused | `PAUSED` |
| Ended | `ENDED` |

- **Stripe status mapping:** `trialing` → `TRIALING`, `active` → `ACTIVE`, `past_due` → `PAST_DUE`, `canceled` and `incomplete_expired` → `ENDED`. `incomplete` is not stored, because Checkout only completes after the first payment succeeds. `PAUSED` is set by the platform (section 5.6).
- **Period dates:** in current Stripe API versions the period dates are on the subscription item. The sync code reads them there.

## 4. Access

### 4.1 `hasActiveSubscription(organisationId)`

Returns `true` when the organisation is `PUBLISHED` and at least one of these holds:

1. a `TRIAL` row with status `TRIALING` and `now < currentPeriodEnd`
2. a `PAID` row with status `TRIALING` or `ACTIVE`
3. a `PAID` row with status `PAST_DUE` and `now < pastDueSince + 7 days` (SUB-6.2)

Everything else returns `false`, including `PAUSED` and every organisation that is not `PUBLISHED` (SUB-6.8).

- **Time-based ends:** a trial and a grace period end by the clock inside the check. Access stops at the exact time even though the jobs that send the emails run daily.
- **Once per request:** it runs inside `getViewer()` as `entitlements.subscription`, and the result is reused for the rest of the request (`01` design section 6.1).
- **Webhook delay:** a renewal stays `ACTIVE` until Stripe reports otherwise, so a late webhook never removes access by mistake. The daily reconciliation catches missed webhooks (section 9.3).

### 4.2 Gated features (SUB-3)

| Feature | Policy | Uses `hasActiveSubscription` for |
|---|---|---|
| Players directory and player profiles | `canViewPlayers` | managers |
| Create, edit, close, delete offers | `canManageOffers` | the manager's organisation |
| View applications and change their status | `canViewApplications` | the manager's organisation |

- **Not gated (SUB-3.2):** signing in, editing the organisation and own profile, the public organisation page, organisation and offer directories, messaging and the inbox. Their policies never call `hasActiveSubscription`.
- **Players and staff (SUB-3.3):** the policies return before the subscription check.
- **Same rule everywhere (SUB-3.4, SUB-3.5):** the check takes an organisation id only, so it applies to every organisation type and to all of its managers.
- **Gate (SUB-3.6):** a gated page renders the shared gate with "You need to be subscribed" and a link to `/pricing`. A past-due organisation after the grace period sees the banner from section 5.4 instead.

### 4.3 Buying policy

`canBuyPlan(viewer, plan)` is true when all of these hold (SUB-1.2, SUB-4.1):
- the viewer is a verified manager with an `ACTIVE` membership
- the organisation is `PUBLISHED`
- the plan is active and matches the organisation's type
- the organisation has no `PAID` subscription that is not `ENDED`

`canManageBilling(viewer)` (subscription page, cancel, undo, switch, Portal) needs a verified manager with an `ACTIVE` membership, whatever the organisation status.

## 5. Lifecycle

### 5.1 Free trials given by staff (SUB-2)

- **Give a trial (SUB-2.1):** staff choose a plan of the organisation's type and an end date in the future. The organisation must be `PUBLISHED` and have no running trial and no `PAID` subscription that is not `ENDED`. The service inserts a `TRIAL` row with status `TRIALING`, writes a `billing.trial.give` audit event and queues the "trial started" email.
- **More than one trial (SUB-2.6):** allowed over time, one at a time. Each one has its own row and audit event.
- **Extend a trial:** staff change `currentPeriodEnd`. Audited.
- **End (SUB-2.3):** access stops by the clock (section 4.1). The daily billing job sets `ENDED` with `endedReason = TRIAL_ENDED`, sets `accessEndedAt` and queues the "trial ended" email. Nothing is charged.
  - If a paid subscription was bought during the trial, it takes over at that moment and no "trial ended" or subscribe-again email is sent.
- **Ending a trial early:** staff cancel it (section 7.2). This does not change a paid subscription bought during the trial; staff cancel that separately if needed.

### 5.2 Buying (SUB-4)

1. The manager presses "Subscribe" on `/pricing` or the subscription page. A Server Action checks `canBuyPlan`.
2. The service locks the organisation, creates the Stripe Customer if there is none, and expires any Checkout session still open for this organisation.
3. It creates a Checkout session:
   - `mode: 'subscription'`, the plan's current Price, `customer`, `client_reference_id = organisationId`
   - `subscription_data.metadata` with the organisation and plan ids
   - `allow_promotion_codes: true` (SUB-5.1)
   - `payment_method_collection: 'always'`, so a 100% code still collects a card (SUB-5.4)
   - `billing_address_collection: 'required'`, phone number collection on, and a custom field for the company name (SUB-4.2)
   - `customer_update` for name and address, so the details are saved on the Customer
   - card payments only, which include Apple Pay and Google Pay
   - the terms text and renewal statement from section 11 (SUB-10.1)
   - during a running trial: `subscription_data.trial_end` = the trial's end (SUB-2.5). Checkout needs a trial end at least 48 hours ahead, so a trial ending sooner uses now + 48 hours. The organisation gets up to 2 extra free days rather than losing trial time.
   - `success_url = /billing/success?session_id={CHECKOUT_SESSION_ID}`, `cancel_url = /pricing`
4. The browser is redirected to Checkout.

- **Success (SUB-4.3):** the success page fetches the session from Stripe and runs the same `syncSubscription` as the webhook, so access starts at once even if the webhook is late. It shows the plan, price, next payment date and a link to the subscription page. The receipt email is sent from `invoice.paid` (section 10).
- **Failure (SUB-4.4):** Checkout shows the card issuer's reason on its own page and lets the manager try another card. Leaving Checkout returns to `/pricing` with nothing created.
- **Double purchase (SUB-4.5):** step 2 makes a second open session impossible in normal use. If two sessions still complete, the second `checkout.session.completed` finds an existing paid subscription; the service cancels the new one at once, refunds its first payment in full and alerts staff.

### 5.3 Discount codes (SUB-5)

- **Created by staff (SUB-8.6):** one Stripe Coupon (percent off, duration, `applies_to.products` from the chosen plans) and one Promotion Code (the upper-case code, `expires_at`, `max_redemptions`). Both ids are stored in `DiscountCode`.
- **Not case-sensitive (SUB-5.2):** codes are stored upper-case, and Stripe matches promotion codes without regard to case.
- **Checks at payment (SUB-5.3):** Checkout itself refuses unknown, expired, used-up and wrong-plan codes and keeps the full price.
- **Changing limits:** Stripe does not allow changing a promotion code's expiry or maximum uses. The service deactivates the old promotion code and creates a new one with the same code, the new expiry and `maxRedemptions − timesRedeemed`.
- **Expire:** sets the promotion code inactive. Subscriptions already using it keep the discount for its duration.
- **Usage:** `timesRedeemed` and the subscription's `discountCodeId` are updated from webhooks.
- **End of a discount (SUB-5.4):** Stripe charges the full price from the first invoice after the coupon's duration.

### 5.4 Renewals, failed payments and grace (SUB-6.1 to SUB-6.4)

- **Renewal paid (SUB-6.1):** `invoice.paid` stores the `Payment`, updates the period and queues the receipt email.
- **Renewal failed (SUB-6.2):**
  - `invoice.payment_failed` sets `PAST_DUE`, sets `pastDueSince` on the first failure only, records the attempt on the `Payment`, and emails the managers at once with an "Update payment method" link (a Portal session).
  - Staff are notified (SUB-9.2).
  - Stripe Smart Retries retry over the following days: up to 8 attempts within 2 weeks.
  - A renewal that needs 3-D Secure (`invoice.payment_action_required`) is handled the same way, and the email links to Stripe's hosted invoice page.
- **Grace ends (SUB-6.3):** after 7 days `hasActiveSubscription` returns `false`. The daily job sets `accessEndedAt`, sends the "access stopped" email once and turns on the banner: "Your payment failed. Update payment method" on every dashboard page for that organisation's managers.
- **Recovered (SUB-6.4):** a later `invoice.paid` sets `ACTIVE`, clears `pastDueSince` and `accessEndedAt`, and queues the "payment recovered" email. Access returns on the next request.
- **All retries failed:** Stripe is set to cancel the subscription. `customer.subscription.deleted` sets `ENDED` with `endedReason = NON_PAYMENT`. `accessEndedAt` keeps the date access stopped, so the subscribe-again reminders count from then (SUB-6.10).

### 5.5 Cancel, undo and plan switch (SUB-6.5 to SUB-6.7)

These run on the platform's subscription page through the Stripe API. They are turned off in the Portal (section 6.2) so that a waiting plan switch is always handled correctly.

- **Cancel (SUB-6.5):**
  - a paid subscription: release the schedule if there is one, clear `scheduledPlanId` (SUB-6.7), then set `cancel_at_period_end: true`. Access continues until `currentPeriodEnd`.
  - a paid subscription still in its Stripe trial (bought during a staff trial): the same, so it ends at the trial end without charging.
- **Undo (SUB-6.6):** before the period ends, set `cancel_at_period_end: false`. A dropped plan switch is not restored; the manager can choose it again.
- **After the end:** `customer.subscription.deleted` sets `ENDED` with `endedReason = CANCELLED` and `accessEndedAt`. Subscribing again is a new purchase (section 5.2).
- **Plan switch (SUB-6.7):** only between the monthly and annual plan of the organisation's type.
  1. Create a Subscription Schedule from the subscription.
  2. Set two phases: the current Price until `currentPeriodEnd`, then the other plan's current Price, with `end_behavior: 'release'` and no proration.
  3. Store `scheduledPlanId` and `stripeScheduleId`.

  When the next period starts, the webhook updates `planId` and `planPriceId` and clears both fields. "Cancel the switch" releases the schedule.

### 5.6 Pause and resume when unpublished (SUB-6.8)

Stripe's `pause_collection` stops charges but lets the period run on, so the platform stores the remaining time itself.

- **Pause (when staff unpublish, `05` ADM-8.5):** in the same service call as the status change:
  - `pausedRemainingSeconds` = `currentPeriodEnd − now`, or 0 if the subscription is `PAST_DUE` (an unpaid period gives no time back)
  - a paid subscription gets `pause_collection: { behavior: 'void' }` and its schedule is released, keeping `scheduledPlanId`
  - status `PAUSED`, `pausedAt = now`
  - a running trial is paused the same way, without any Stripe call
  - "subscription paused" email queued
- **Resume (when staff republish):**
  - remaining time above 0: update the Stripe subscription with `trial_end = now + pausedRemainingSeconds`, `proration_behavior: 'none'`, and clear `pause_collection`. The next charge is at the end of that free time, at the subscriber's price.
  - remaining time 0: clear `pause_collection` and set `billing_cycle_anchor: 'now'`, so a payment is taken at once and normal failed-payment handling applies.
  - a trial: `currentPeriodEnd = now + pausedRemainingSeconds`.
  - a waiting plan switch is scheduled again.
  - status from the next sync; "subscription resumed" email queued.
- **Discounts while paused:** a repeating discount counts calendar months in Stripe, so months spent paused use it up. The platform does not restore them on resume.
- **Ordering:** the Stripe call runs before the database commit. If it fails, the unpublish or republish is refused with an error and nothing changes. Both sides are compared again by reconciliation (section 9.3).

### 5.7 Reminders (SUB-2.4, SUB-6.9, SUB-6.10)

The daily billing job runs at 09:00 UK time. Each reminder inserts a `BillingReminder` row first, so a re-run never sends it twice.

| Reminder | Selection |
|---|---|
| Trial ends in 7 days / 1 day | `TRIAL`, `TRIALING`, `currentPeriodEnd` in that day, and no paid subscription waiting |
| Annual renewal in 14 / 7 / 1 days | `PAID`, annual plan, `ACTIVE` or `TRIALING`, not `isCancelledAtPeriodEnd`, `currentPeriodEnd` in that day |
| Subscribe again after 1 / 2 / 7 / 30 / 180 days | the organisation's latest subscription has `accessEndedAt` that many days ago, the organisation is `PUBLISHED` and `hasActiveSubscription` is false |

- Monthly plans get no renewal reminders.
- The subscribe-again reminders stop by themselves once the organisation subscribes, because the selection requires no active subscription.
- The same job ends trials (section 5.1) and handles the end of grace periods (section 5.4).

## 6. Manager's subscription page

### 6.1 Page (SUB-7.1, SUB-7.3)

`/dashboard/subscription`, visible with `canManageBilling`. It reads only local tables.

- **With a subscription:** plan, shown status, price and billing period, start date, who bought it ("Deleted user" after deletion), card brand and last 4 digits, next renewal date or trial end date, a waiting plan switch, billing details, and the invoice list.
- **Invoices:** from `Payment`. "Download PDF" opens `/billing/invoices/{paymentId}`, which checks `canManageBilling` for that organisation, fetches the invoice from Stripe and redirects to its short-lived PDF link.
- **Without a subscription:** "Not currently subscribed" and the plans for the organisation's type, with the buy state from `canBuyPlan`.
- **During a staff trial:** the trial's plan and end date, and the plans to buy (SUB-2.5).

### 6.2 Actions (SUB-7.2)

| Action | Where |
|---|---|
| Update payment method | Stripe Customer Portal |
| Update billing details | Stripe Customer Portal |
| Cancel, undo cancellation | Platform page (section 5.5) |
| Switch plan, cancel a waiting switch | Platform page (section 5.5) |

- **Portal session:** a Server Action checks `canManageBilling` and creates a Portal session for the organisation's Customer with `return_url` set to the subscription page.
- **Portal configuration:** payment method update on; name, email, address and phone update on; invoice history on; subscription cancel off; subscription update off.
- **Card and details sync:** `customer.updated` and `payment_method.attached` update `BillingAccount`.

## 7. Staff billing tools (SUB-8)

All tools need `billing.view` or `billing.manage` (`05` design section 4.1). Every action writes a `billing.*` audit event in the same transaction as the local change and passes an idempotency key to Stripe.

### 7.1 Lists and history

- **Subscriptions (SUB-8.1):** organisation, plan, shown status, price, start date, next payment or end date. Filters: status, plan, organisation type, start date range, end date range. Cursor paging.
- **Payment history (SUB-8.5):** on each organisation's staff page: every `Payment` with status, failed attempts and the last failure reason, and every `Refund`.
- **Statistics (SUB-8.7):** from the local tables (`05` design section 5).

### 7.2 Actions (SUB-8.2)

| Action | Stripe call | Local effect |
|---|---|---|
| Give or extend a trial | none | Section 5.1 |
| Cancel at period end | `cancel_at_period_end: true` (schedule released) | `isCancelledAtPeriodEnd` |
| Cancel now | cancel the subscription, no proration, no automatic refund | `ENDED`, `endedReason = STAFF`, `accessEndedAt = now` |
| Cancel a trial | none | `ENDED`, `endedReason = STAFF` |
| Extend a period | `trial_end` = the new date, `proration_behavior: 'none'` | New `currentPeriodEnd`; the time added is free |
| Change plan, same billing period | change the item's Price, `proration_behavior: 'none'` | New price from the next renewal |
| Change plan, other billing period | Subscription Schedule (section 5.5) | `scheduledPlanId` |
| Apply a discount | add the code's Coupon to the subscription | `discountCodeId` |
| Refund | refund on the invoice's payment, full or part | `Refund` row; `amountRefundedPence` |

- **Refunds (SUB-8.3):** staff enter the amount (up to what is left to refund) and a reason. The money goes back to the original payment method.
- **Full refund (SUB-8.4):** after a refund that brings the total refunded to the full amount, the dialog asks "Cancel this subscription now?" with "Cancel now" and "Keep subscription".
- **Organisation delete (SUB-8.8):** `deleteOrganisation` (`03` design section 9) refuses while any `Subscription` row of the organisation is not `ENDED`, including a paused one or one set to cancel at period end. The refusal names the subscription and links to "Cancel now".

## 8. Plans and price changes (SUB-1)

- **Pricing page (SUB-1.1):** lists every active plan by organisation type with a monthly / annual switch. It is cached with the `plans` tag. Each buy button shows its state from `canBuyPlan`, with the reason when it cannot be used: sign in, other organisation type, organisation not published, or already subscribed.
- **Add a plan (SUB-1.3, `plans.manage`):** creates the Stripe Product and Price, then the `Plan` and `PlanPrice` rows.
- **Change a price:** creates a new Stripe Price on the same Product and a new `PlanPrice`, and points `currentPriceId` at it. New purchases use it; existing subscribers keep their `planPriceId`.
- **Move subscribers to a new price:** an Administrator action, per subscription or for every subscriber of a plan. It changes the item's Price with `proration_behavior: 'none'`, so the new price applies from each subscriber's next renewal, and emails the managers at the time of the move ("plan changed", SUB-9.1). There is no minimum notice period.
- **Retire a plan:** `isActive = false` and the Stripe Price is archived. Existing subscribers continue until they cancel or are moved.
- Every plan change updates the `plans` cache tag and is audited.

## 9. Stripe webhooks and reconciliation

### 9.1 Endpoint

`POST /api/stripe/webhook`, a Route Handler:

1. Read the raw body with `request.text()` and verify the `Stripe-Signature` header with the webhook secret. Reject anything that fails.
2. Insert a `WebhookEvent` row with the event id. If the id exists and `processedAt` is set, return 200 without doing anything (idempotency).
3. Process the event in one database transaction, then set `processedAt`.
4. On an error, store it on the row and return 500, so Stripe retries. Repeated failures raise a staff alert (`01` design section 17).

- **Order independence:** events can arrive out of order or more than once. For subscription events the handler fetches the current subscription from Stripe and runs `syncSubscription(stripeSubscriptionId)`, which overwrites the local row with Stripe's current state. Events are never applied as increments.
- **Emails:** the handler compares the old and new local state and queues outbox emails only for real changes (for example `ACTIVE` → `PAST_DUE`), so a repeated event sends nothing.

### 9.2 Events handled

| Event | Handling |
|---|---|
| `checkout.session.completed` | Link the subscription to the organisation, `syncSubscription`, double-purchase check (section 5.2), discount usage |
| `customer.subscription.created`, `.updated` | `syncSubscription` |
| `customer.subscription.deleted` | `ENDED`, `endedReason`, `accessEndedAt` |
| `invoice.paid` | Store `Payment`, clear past due, receipt or recovery email |
| `invoice.payment_failed` | Section 5.4 |
| `invoice.payment_action_required` | Section 5.4 |
| `charge.refunded`, `refund.updated` | Update `Refund` and `amountRefundedPence`; refund email (covers refunds made in the Stripe dashboard too) |
| `customer.updated`, `payment_method.attached` | Update `BillingAccount` |
| `subscription_schedule.released`, `.canceled` | Clear `scheduledPlanId` and `stripeScheduleId` if they match |

### 9.3 Reconciliation (daily job)

- For every local `PAID` subscription that is not `ENDED`, plus every Stripe subscription updated in the last 2 days, run `syncSubscription`.
- Any difference that changed status is logged and reported to staff.
- `WebhookEvent` rows that failed are processed again.
- `PAUSED` rows are checked to still have `pause_collection` set in Stripe.

## 10. Notifications (SUB-9)

All emails go to `managersToNotify(organisationId)` through the outbox (`01` design section 9). Each one also creates an in-app notification for the same managers.

| Email | Trigger |
|---|---|
| Subscription started / trial started | `checkout.session.completed` / staff gives a trial |
| Receipt | `invoice.paid` with an amount above 0 (link to the invoice PDF) |
| Trial ending | Reminder job (section 5.7) |
| Annual renewal near | Reminder job |
| Payment failed | `invoice.payment_failed`, `invoice.payment_action_required` |
| Payment recovered | `invoice.paid` after `PAST_DUE` |
| Access stopped | Daily job at the end of the grace period |
| Subscription cancelled | Cancel by a manager or staff (with the access end date) |
| Paused / resumed | Unpublish / republish (section 5.6) |
| Subscription or trial ended | `customer.subscription.deleted` / trial end job |
| Subscribe again | Reminder job |
| Refund made | `charge.refunded` |
| Plan changed | Plan switch takes effect, staff change, price move |

- **Staff (SUB-9.2):** failed payments and refunds notify every staff member by email and in the app.
- **No card data in emails:** at most the card brand and last 4 digits.

## 11. Legal and retention (SUB-10)

- **Payment page (SUB-10.1):**
  - Checkout shows the price and billing period itself.
  - `custom_text.submit` states "Renews automatically every month / year until cancelled."
  - `consent_collection.terms_of_service: 'required'` with text linking to the Terms and Conditions and the Refund Policy.
- **No VAT (SUB-4.6):** no tax settings in Stripe; invoices show the full price with no VAT line and no VAT number field. If Offload registers for VAT later, Stripe Tax is turned on and the invoice template changed.
- **Refund Policy page (SUB-10.3):** static content stating that refunds, including for unused time after cancellation, are decided case by case.
- **Retention (SUB-10.2):**
  - `BillingAccount`, `Subscription`, `Payment` and `Refund` rows are kept for 6 years after the last payment, also after the organisation or a manager is deleted. A deleted organisation keeps its name for this (`03` design section 9); a deleted buyer shows as "Deleted user".
  - The Stripe Customer is not deleted with the organisation, so its invoices remain available.
  - A yearly job deletes local billing rows older than 6 years and then deletes the Stripe Customer.
  - `billing.*` and `subscription.*` audit events are kept for 6 years (`05` design section 10).
