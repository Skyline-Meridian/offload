# 05. Dashboard Design

Implements `docs/requirements/05. admin_section.md`. Shared parts (viewer, policies, outbox, files, audit conventions) are in `01. general_design.md`.

---

## 1. Structure

- **One dashboard for every role:** a single area under `/dashboard` with one layout. The layout builds the menu from the viewer's role and organisation type, and shows only that role's sections (ADM-1.1).
- **Start page (ADM-1.2):** `/dashboard` opens on the profile summary for players and managers, and on statistics for staff. For players and managers, anything missing for verification is shown at the top.
- **Staff sections:** they live under `/dashboard/staff/…`. Their layout returns 404 to anyone who is not staff, so the area is not advertised (ADM-4.1).
- **Unmet conditions (ADM-1.6):** a section whose condition is not met (verification, organisation or subscription) shows a gate with the reason and the next step, instead of being hidden.
- **Staff Server Actions:** every one calls `requirePermission(permission)` and writes an audit event in the same transaction as the change.
- **Caching:** dashboard pages render per request and are never cached.

## 2. Sections for every user

| Section | Design |
|---|---|
| Notifications (ADM-1.3) | Panel with the unread count; opening it marks everything in it as read (`01` design section 9) |
| Account settings (ADM-1.4) | Change email, change password, sign out of all devices, newsletter opt-in or opt-out, download my data, delete my account |
| Inbox | Conversation threads; managers get the Personal / Organisation switch (`04` design section 3.3) |

- **Change email (ADM-1.5):** the new address goes into `pendingEmail` and a verification link is sent there. The account email changes only when the link is used (`01` design section 5.4).
- **Change password:** requires the current password. Other sessions are ended.
- **Download my data:** queues the export job and emails a signed link (`01` design section 14.1).
- **Delete my account:** asks for confirmation and the password, then runs `deleteAccount`. The last verified manager of an organisation and the last Administrator are refused with an explanation (`01` design section 14.2).

## 3. Player and manager sections

- **Player:** profile editor, verification, inbox and applications. The behaviour is in `02` design section 3 and `04` design section 2.3.
- **Manager:**
  - **Profile:** the `User` fields from `03` section 4.
  - **Verification:** email status and identity document upload.
  - **Organisation:**
    - With no current membership: "Add organisation" or "Claim an existing organisation".
    - Otherwise: view and edit (`03` design section 4), "Changes awaiting review", the status and its reason, the names of the other managers (ADM-3.2), "Send for review again" for a rejected organisation (ADM-3.4), and "Remove organisation from my profile" (`03` design section 5).
  - **Offers, applications and subscription:** shown only to verified managers with an active membership (ADM-3.1). Offers and Applications show the upgrade gate without an active subscription.
- **Rejected manager (ADM-3.5):** the verification section offers "Upload a new document". For a rejected claim it also offers "Choose another organisation" and "Register a new organisation".

## 4. Staff accounts and permissions

### 4.1 Permissions

Permissions are defined in code and mapped to the two staff roles, so changing the split means editing one map.

| Permission | Administrator | Offload Admin |
|---|---|---|
| `stats.view` | ✓ | ✓ |
| `verification.review` | ✓ | ✓ |
| `users.view`, `users.edit`, `users.suspend`, `users.delete`, `users.export` | ✓ | ✓ |
| `organisations.view`, `organisations.edit`, `organisations.unpublish`, `organisations.delete`, `organisations.removeManager` | ✓ | ✓ |
| `offers.moderate` (see the public details, close with a reason) | ✓ | ✓ |
| `billing.view`, `billing.manage` (trials, cancel, extend, change plan, discounts, refunds) | ✓ | ✓ |
| `reference.manage` | ✓ | ✓ |
| `audit.view` | ✓ | ✓ |
| `staff.manage`, `users.changeRole` | ✓ | – |
| `settings.manage`, `plans.manage` | ✓ | – |

Some things have no permission at all, so no staff code path exists for them (ADM-4.6, ADM-4.7):
- creating, editing or deleting offers
- seeing or changing applications
- reading other users' messages
- signing in as another user

The only offer action open to staff is `closeOfferForViolation(offerId, reason)` (section 8).

### 4.2 Staff accounts

- **Invitation (ADM-4.2, ADM-4.4):** an Administrator invites a staff member by email. The invitation link (valid 7 days) lets them set a password. Accepting sets `emailVerifiedAt`. Staff need no document verification and are never deleted as unverified.
- **Role changes (ADM-4.2):**
  - Promoting a player or manager to staff stores `previousRole`.
  - "Return to previous role" restores it.
  - No other role change exists, so players and managers cannot be changed into each other.
  - A role change ends the user's sessions.
- **Last Administrator (ADM-4.3):** `assertNotLastAdministrator(userId)` locks the Administrator rows and counts them. It runs with removal, suspension, deletion and role change, and refuses if no other Administrator would remain.
- **Sign-in (ADM-4.5):** staff sign in with email and password. There is no second factor.
- **Staff inbox (ADM-4.8, ADM-4.9):** staff write as user parties (`04` design section 3.1). They are left out of every directory and have no profile page. Nothing stops a user from replying to them or writing to them.

### 4.3 Staff notifications (ADM-4.10)

- **New item to review:** each new item (player, manager, organisation, or change awaiting review) queues one email and one in-app notification for every staff member.
- **Daily summary:** a daily job emails every staff member the counts and oldest waiting times for each list.
- **Menu counts:** each verification list shows its waiting count next to it in the menu, from one grouped count query per request.

## 5. Statistics (ADM-5.1, ADM-5.2)

- **User and organisation counts:** `COUNT(*) FILTER (WHERE …)` queries grouped per entity, run in parallel.
- **Messages and applications:** plain counts only. No statistics query reads message bodies.
- **Billing figures:** active subscriptions per plan, monthly recurring revenue, failed payments in the last 30 days and renewals in the next 30 days. They come from the local billing tables, which webhooks keep in step with Stripe (`06` design), not from live Stripe calls.
- **Monthly recurring revenue:** monthly plans at their price, plus annual plans at price ÷ 12. It counts active and past-due paid subscriptions after recurring discounts. Trials count as zero.
- **Weekly registrations:** grouped by week and role.
- **Links:** each user and organisation figure links to the matching filtered list.

## 6. Verification

### 6.1 Model

```prisma
enum VerificationSubject { PLAYER  MANAGER  ORGANISATION }
enum VerificationStatus  { PENDING  APPROVED  REJECTED  REVOKED  SUPERSEDED }

model VerificationRequest {
  id              String @id @default(uuid(7)) @db.Uuid
  subject         VerificationSubject
  userId          String?                 // PLAYER, MANAGER
  organisationId  String?                 // ORGANISATION; for MANAGER, the organisation registered or claimed
  membershipId    String?                 // MANAGER: the membership this approval activates
  isClaim         Boolean @default(false) // MANAGER: chose an existing organisation
  documents       VerificationDocument[]  // private Files
  status          VerificationStatus @default(PENDING)
  submittedAt     DateTime @default(now())
  decidedAt       DateTime?
  decidedById     String?
  reason          String?
  possibleDuplicateOfId String?           // ORGANISATION only (`03` design section 6)
  @@index([subject, status, submittedAt])
}

model VerificationDocument {
  requestId String
  fileId    String
  @@id([requestId, fileId])
}
```

- **Standard columns:** left out above, as in every design file: `createdAt`, `updatedAt`, `createdById`, `updatedById`, and `@db.Uuid` on foreign keys (`01` design section 4).
- **Documents:** `VerificationDocument` links a request to its files with foreign keys, so a request can never point at a file that no longer exists. A plain array of ids could not be checked that way.

- **New uploads:** each new document upload creates a new request, and an older pending request becomes `SUPERSEDED`. The history keeps every decision.
- **Changes awaiting review:** sensitive organisation changes use `OrganisationChangeRequest` (`03` design section 4.1).
- **State on the user and organisation:** the same service call that decides a request also updates `User.documentStatus`, the membership status, `PlayerProfile.listedAt` and the organisation status.

### 6.2 Lists (ADM-6.1, ADM-6.2)

- **Pages:**
  - `/dashboard/staff/verify-users?tab=players|club-managers|union-managers|college-university-managers|brand-managers`
  - `/dashboard/staff/verify-organisations?tab=clubs|unions|colleges-universities|brands`
  - `/dashboard/staff/changes`
- **Queries:** one query per list on `VerificationRequest` (or `OrganisationChangeRequest`), filtered by subject and organisation type and joined for the display columns. Lists are searchable and sortable, oldest first by default, and show "Nothing to review" when empty.
- **Keeping documents:** identity and organisation documents are kept for as long as the account or organisation exists, so a verification can be checked later. They are deleted with the account or organisation (`01` design section 14.2).
- **Documents (ADM-6.3):** shown inside the dashboard through `/files/{id}`. Images are shown inline and PDFs in the browser's viewer. Every opening is audited.

### 6.3 Decisions

| Action | Effect |
|---|---|
| Approve a player | `documentStatus = VERIFIED`, `listedAt` set, decision recorded, player notified (ADM-6.4) |
| Approve a manager | `documentStatus = VERIFIED`, membership `ACTIVE`, manager notified (ADM-6.4) |
| Approve an organisation | Status `PUBLISHED`, `publishedAt` set, managers notified; managers are not approved by this (ADM-6.5) |
| Approve a change | New values applied (ADM-6.6) |
| Reject | A reason is required and sent; what happens next follows ADM-3.4 and ADM-3.5 (ADM-6.7) |
| Revoke a player | `documentStatus = REVOKED`, `listedAt` cleared (ADM-6.8) |
| Revoke a manager | `documentStatus = REVOKED`, membership `REMOVED`; refused for the last verified manager (ADM-6.8) |
| Revoke an organisation | Same as unpublishing (section 7.2) |
| Bulk approve | At most 50 selected items per action, one transaction each, results per item; no bulk reject (ADM-6.9) |

## 7. Users and organisations

### 7.1 Users (ADM-7)

- **Lists:** cursor paging, with filters for role, organisation type, verification state, date joined, country and status.
- **Editing (ADM-7.2):** staff use the same validation schemas as the users' own forms, plus a staff-only panel. Staff can change email, name and date of birth.
  - Staff changes never send a verified user back to review.
  - They are audited with old and new values.
  - A staff email change takes effect at once.
- **Password reset:** staff can send a reset link.
- **Suspend (ADM-7.3, ADM-7.4):**
  - Sets `status = SUSPENDED` and ends all sessions and realtime connections.
  - Clears `listedAt` for players and withdraws open applications.
  - Other users keep the conversation history but cannot send new messages to the suspended user.
  - Refused for the last verified manager and the last Administrator.
- **Reactivate:** restores `ACTIVE`, and sets `listedAt` again for a verified player.
- **Delete:** runs `deleteAccount` (`01` design section 14.2).
- **Export (ADM-7.6):** a worker job writes a CSV with name, role, organisation type, email, verification state and newsletter opt-in to `private/exports/`. Staff get a signed link valid 1 hour. Each export and its filter are audited.

### 7.2 Organisations (ADM-8)

- **Lists:** filters for type, status, country and subscription status.
- **Editing (ADM-8.2):** staff can edit every field, whatever the status. Changes apply at once, skipping change requests, and are audited with old and new values. The page also shows the managers, the subscription and counts of offers and applications.
- **Remove a manager (ADM-8.3):** sets the membership to `REMOVED` and revokes the verification. It is guarded by `assertNotLastVerifiedManager`. There is no "add manager" action.
- **Unpublish (ADM-8.5, ADM-8.6):** a reason is required. The status becomes `UNPUBLISHED`, the managers are notified, and the subscription is paused (`06` design section 5.6).
- **Republish:** returns the status to `PUBLISHED` and resumes the subscription.
- **Duplicates (ADM-8.4):** staff unpublish one record, then cancel or refund its subscription in the billing tools.
- **Delete (ADM-8.7):** runs the guarded `deleteOrganisation` (`03` design section 9).
- **Organisation type (ADM-8.8):** there is no way to change it.

## 8. Offer moderation (ADM-9)

- **Seeing an offer:** staff see only the offer's public details.
- **Closing:** `closeOfferForViolation(offerId, reason)` sets `CLOSED`, `closedByStaffId` and `closedReason`, then notifies the managers.
- **Afterwards:** the managers' offers section shows "Closed by Offload" with the reason, and "Copy as new offer" is not available for that offer (`04` design section 1.2).
- **No other actions:** staff cannot reopen, edit or delete an offer, and cannot see its applications.

## 9. Billing and reference data

- **Billing (ADM-10.1):** staff billing tools are described in `06` design section 7. Both staff roles can use them.
- **Reference data (ADM-11.1):** one list editor (label, sort order, active) covers positions, soft skills, game skills, qualifications, leagues and industries. Retiring an entry sets `isActive = false`.

## 10. Audit log (ADM-12)

```prisma
model AuditEvent {
  id             String @id @default(uuid(7)) @db.Uuid
  actorKind      ActorKind                  // USER | SYSTEM
  actorId        String?                    // USER: the user or staff member; null for SYSTEM
  systemActor    String?                    // SYSTEM: which part acted, e.g. "job:offer-expiry", "webhook:stripe", "migration"
  actorRole      UserRole?
  action         String                     // e.g. "auth.signin", "verification.approve", "message.sent", "billing.refund"
  subjectType    String                     // User, Organisation, Offer, Application, Conversation, Subscription, File, ...
  subjectId      String
  relatedUserIds String[]
  relatedOrgId   String?
  before         Json?
  after          Json?
  ip             String?
  createdAt      DateTime @default(now())  // append-only: actorId takes the place of createdById, and there is no updatedAt
  @@index([subjectType, subjectId, createdAt])
  @@index([actorId, createdAt])
  @@index([relatedOrgId, createdAt])
}
```

- **What is recorded (ADM-12.1):** the events listed in ADM-12.1, written in the same transaction as the change. A trial given by staff is recorded as a billing event (SUB-2.6).
- **What is never recorded (ADM-12.2):** each action type has a list of allowed fields, and `audit()` rejects anything else. `message.sent` stores the conversation, sender and recipient only, never the message text. A unit test checks that no audit payload can contain a message body, password, token, document content or card detail.
- **Search and timelines (ADM-12.3):** staff can search by user, organisation, event type and date range. Each user's and organisation's staff page has a timeline that combines `actorId`, `relatedUserIds` (GIN index) and `relatedOrgId`.
- **No changes (ADM-12.4):** the application's database role can only `INSERT` and `SELECT` on this table.
- **Retention (ADM-12.5):** a daily job deletes events older than 2 years. Events whose action starts with `billing.` or `subscription.` are kept for 6 years. The retention job runs under a separate database role that may delete.
- **Deleted users (ADM-12.6):** audit events keep the user's id. Names and emails are never stored in `before`/`after` for user identity. They are read from the `User` row when shown, so after deletion the tombstone shows "Deleted user".

## 11. Settings, terms and support (ADM-13)

- **Settings (ADM-13.1):** a `Setting` table (key, JSON value, updated by, updated at) holds the email sender name and address, the support email address and the current terms version. It is read once per request.
- **New terms version (ADM-13.2):** the viewer gets `mustAcceptTerms` when `User.termsVersion` is not the current version. Every page then shows a banner with "Read and accept" until the user accepts. Using the platform is not restricted.
- **Website content (ADM-13.3):** kept in code and changed through development. There is no content editing in the dashboard.
- **Contact form (ADM-13.4):** a public form with the same bot protection as registration (`01` design section 5.4). It queues an email to the support address and stores nothing.
