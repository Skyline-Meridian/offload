# 04. Offers, Applications, Messaging and Notifications Implementation

How to build `docs/architectural design/04. offers_and_applications.md` for `docs/requirements/04. offers_and_applications.md`. Read `01. general_implementation.md` first.

---

## 1. Schema

Add the models from the design with the standard columns: `Offer`, `OfferPosition`, `OfferSkill`, `Application`, `Conversation`, `ConversationParty`, `Message` (append-only: `createdAt`, `createdById` only), and `Notification` if not already added in phase 0.

Raw SQL:

```sql
-- a published (or later) offer must be complete (OFF-1.8)
ALTER TABLE "Offer" ADD CONSTRAINT offer_complete CHECK (
  status IN ('DRAFT', 'PENDING') OR
  (title IS NOT NULL AND description IS NOT NULL AND paid IS NOT NULL
   AND "publishedAt" IS NOT NULL AND "expiresAt" IS NOT NULL)
);
CREATE INDEX offer_title_trgm ON "Offer" USING gin ((immutable_unaccent(lower(title))) gin_trgm_ops);
-- a party is either a user or an organisation
ALTER TABLE "ConversationParty" ADD CONSTRAINT party_kind CHECK (
  (kind = 'USER' AND "userId" IS NOT NULL AND "organisationId" IS NULL) OR
  (kind = 'ORGANISATION' AND "organisationId" IS NOT NULL AND "userId" IS NULL)
);
CREATE UNIQUE INDEX party_unique ON "ConversationParty" ("conversationId", kind, COALESCE("userId", "organisationId"));
REVOKE UPDATE, DELETE ON "Message" FROM offload_app;
```

## 3. Offers

### 3.1 Routes

| Route | Page |
|---|---|
| `/offers` | Directory (login required) |
| `/offers/[id]` | Offer page with Apply / Applied |
| `/dashboard/offers` | Managers' offers section, every status |
| `/dashboard/offers/new` | New offer form |
| `/dashboard/offers/[id]/edit` | Edit form (Draft, Pending, Published only) |

### 3.2 Services

- `saveDraft(viewer, data, offerId?)`: `canManageOffers`; creates or updates an offer with status `DRAFT`. On create, fills `organisationId`, `offeredBy` and, if no location was entered, the organisation's `mapAddress` and `placeId`.
- `publish(viewer, offerId | data)`: validates with `offerPublishSchema`; sets `PUBLISHED`, `publishedAt = now()`, `expiresAt = addDays(publishedAt, 30)`; `updateTag('org-offers:' + orgId)`. The form has two buttons, "Save draft" and "Publish".
- `update(viewer, offerId, data)`: allowed for `DRAFT`, `PENDING`, `PUBLISHED`; never changes `publishedAt` or `expiresAt`. A `PUBLISHED` offer is validated with the publish schema.
- `close(viewer, offerId)`: `PUBLISHED` only → `CLOSED`, `closedAt = now()`.
- `closeForViolation(staff, offerId, reason)`: staff only (`05`); sets `closedByStaffId` and `closedReason`, notifies the managers.
- `deleteOffer(viewer, offerId)`: in a transaction, `count` applications; refuse with "This offer has applications, so it can't be deleted. Close it instead." Drafts have none and can always be deleted.
- `copyOffer(viewer, offerId)`: source must be `CLOSED` or `EXPIRED` and not closed by staff; creates a `DRAFT` with title, description, paid, positions, skills, location and `copiedFromId`; redirects to its edit page.
- Every service checks the offer belongs to the viewer's organisation.

### 3.3 Expiry job

`offer-expiry` (hourly):
1. `UPDATE "Offer" SET status = 'EXPIRED' WHERE status = 'PUBLISHED' AND "expiresAt" <= now() RETURNING id, "organisationId"`; notify managers "Your offer has expired" for each; refresh `org-offers` tags with `revalidateTag`.
2. Offers with `status = 'PUBLISHED' AND "expiresAt" <= now() + interval '3 days' AND "expiryReminderSentAt" IS NULL`: set `expiryReminderSentAt`, notify "Your offer expires in 3 days".

### 3.4 Directory and page

- Base: `status = 'PUBLISHED' AND expiresAt > now() AND organisation.status = 'PUBLISHED'`, newest first (`publishedAt DESC, id DESC`), infinite loading.
- Filters: title search (trigram), organisation type (`offeredBy in`), published date range, positions (any), skills (any), organisation, paid/unpaid.
- Offer page: title, organisation (link and logo), offered by, paid, positions, skills, location (text and `<MapEmbed>`), expiry date (`formatDate`), description (clean HTML).
- Apply area: `canApply` → button opening a dialog with an optional note; existing non-withdrawn application → "Applied" and its status; withdrawn → "Apply again".

## 4. Applications

### 4.1 Applying

`applyToOffer(viewer, offerId, note)` in one transaction:
1. Re-check `canApply` (verified player, offer `PUBLISHED`, not expired, organisation `PUBLISHED`).
2. Look for an existing row on `(offerId, playerId)`:
   - none → insert `SUBMITTED`
   - `WITHDRAWN` → set `SUBMITTED`, new note, `resubmittedAt = now()`
   - any other → return "You have already applied"
3. A unique-key error (`P2002`) from two simultaneous submits is caught and returns "You have already applied".
4. Notify managers. When the organisation has no active subscription the notification and email say "You have a new application. Subscribe to view it." with no player details.

### 4.2 Other actions

- `withdraw(viewer, applicationId)`: own application, any status except `WITHDRAWN`.
- `setStatus(viewer, applicationId, status)`: `canViewApplications`; status in `SHORTLISTED | CONTACTED | REJECTED`; sets `statusChangedAt`, `statusChangedById`; notifies the player.
- Player suspension or deletion withdraws `SUBMITTED`, `SHORTLISTED` and `CONTACTED` applications (called from `05` and `deleteAccount`).

### 4.3 Views

- `/dashboard/applications` (manager): `canViewApplications`, else the subscription gate "Subscribe to view applications". Filters: offer, status. Columns: photo, name, primary position, current club, date, note, status (select), profile link.
- `/dashboard/my-applications` (player): offer, organisation, date, status, Withdraw / Apply again.

## 5. Messaging

### 5.1 Parties and conversations

- `pairKey(a, b)`: party keys `U:<userId>` or `O:<orgId>`, sorted, joined with `|`.
- `findOrCreateConversation(tx, a, b)`:
  ```sql
  INSERT INTO "Conversation" (id, "pairKey", "lastMessageAt", …) VALUES (…)
  ON CONFLICT ("pairKey") DO UPDATE SET "pairKey" = EXCLUDED."pairKey"
  RETURNING id
  ```
  then insert the two `ConversationParty` rows with `ON CONFLICT DO NOTHING`.
- `inboxPartiesFor(viewer)`: the user party, plus the organisation party for a manager with an `ACTIVE` membership.

### 5.2 Sending

`sendMessage(viewer, { target, asOrganisation, body })`:
1. `canMessage(viewer)`; the target exists and is `ACTIVE` (users) or not deleted (organisations); `asOrganisation` only when the viewer is an active manager.
2. `rateLimit('message:' + userId, …)` (`01` section 13).
3. Transaction: find or create the conversation; insert `Message` (`senderUserId`, `senderOrgId` when writing as the organisation); `UPDATE "ConversationParty" SET "unreadCount" = "unreadCount" + 1` for the other party; set `lastMessageAt`; `notify` the recipients; enqueue the message email (section 5.5); `notifyRealtime(tx, { type: 'message.created', conversationId, messageId, parties: [...] })`.
4. Return the saved message so the client can replace its optimistic copy.

Starting a conversation: "Message" buttons on player profiles and organisation pages open `/messages?to=U:<id>` or `?to=O:<id>`, which shows the thread if one exists, or an empty thread with the reply box.

### 5.3 Reading

- `/messages` (two-pane on desktop, list and thread as two screens on mobile), `?box=personal|organisation` for managers, `?c=<conversationId>` for the open thread.
- Conversation list: ordered by `lastMessageAt DESC`, infinite loading, other party name and photo or logo ("Deleted user" / "Deleted organisation"), last message preview (first 80 characters), date, unread dot.
- Thread: newest 50, "Load earlier messages" button for more; bodies rendered as plain text with `whitespace-pre-wrap` and a linkifier that turns `http(s)://` text into links with `rel="nofollow noopener noreferrer"`.
- Opening a thread calls `markRead`: `lastReadAt = now()`, `unreadCount = 0` for the viewer's party, and publishes `conversation.read`.

### 5.4 Realtime

**Server** (`realtime/server.ts`):
- Accept the upgrade only for path `/ws`, matching `Origin`, and a valid session (`01` section 11). Store `{ userId, channels: Set<string> }` per socket, where channels are `U:<userId>` and, for managers, `O:<orgId>`.
- `pg` client: `LISTEN realtime`; on each notification parse the JSON and send it to every socket whose channels include one of the event's `parties`. On `session.revoked` close that user's sockets; on `membership.changed` recompute their channels.
- Ping every 30 seconds; terminate sockets that missed two pongs. At most 10 sockets per user (close the oldest).
- Reconnect to PostgreSQL with backoff if the connection drops, and log it.

**Browser** (`useRealtime()` in the platform layout):
- Opens `wss://<host>/ws` (`ws://localhost:3001/ws` in development, from `NEXT_PUBLIC_REALTIME_URL`).
- Reconnects after 1, 2, 5, 10, then every 30 seconds, and shows the banner "Reconnecting…" while disconnected.
- `message.created` in the open thread → call `getMessage` (Server Action) and append; otherwise update the conversation list and unread totals.
- After reconnecting, fetch messages newer than the last one held for the open thread, and refresh the counts.
- Sending uses `useOptimistic` to show the message at once.

### 5.5 Message emails

- Handler for `email.send` with type `message.new` runs these checks before sending:
  - skip if the recipient party's `lastReadAt` is after the message (read live, MSG-1.15)
  - skip if a `message.new` email for the same conversation and recipient was sent less than 15 minutes ago
- Variables: `firstName`, `senderName`, `link`. Never the message text.

## 6. Notifications

- Navbar bell: the platform layout reads the unread count in the same request as the page (one `count` query), so the number is there on first paint. `notification.created` and `conversation.read` events update it live.
- Opening the panel (react-aria `Popover`) lists the latest 20 and calls `markAllRead`, which sets `readAt` on everything in the panel. `/dashboard/notifications` lists all, with infinite loading.
- Each notification: type label, the linked item's name or title, time ("3 hours ago", full date on hover), and a link.

| Type | Created by |
|---|---|
| `application.new` | `applyToOffer` |
| `application.status` | `setStatus` |
| `message.new` | `sendMessage` |
| `offer.expiring`, `offer.expired` | expiry job |
| `offer.closed_by_staff` | `closeForViolation` |

## 7. Tasks

1. Schema and raw SQL.
2. Offer services with integration tests: draft without title, publish rejects missing fields, expiry date never changes on edit, delete refused with applications, copy creates a draft and the old offer keeps its applications.
3. Offer form, managers' offers section (all statuses with application counts, "Closed by Offload" with the reason), directory, offer page.
4. Expiry job with tests for the reminder sent once.
5. Applications: apply, apply twice, withdraw and apply again, status changes, the subscribe-to-view notification.
6. Messaging services: `pairKey` unit tests, one conversation per pair under concurrency, unread counts, organisation inbox visible to every manager, staff limited to their own conversations, deleted parties shown as tombstones.
7. Realtime server and hook; an integration test that a committed message produces an event and a rolled-back one does not.
8. Messages UI with optimistic sending and reconnect banner.
9. Notifications: bell, panel, page.
10. End-to-end: a player applies and the manager sees the application; a player messages a club and a manager replies, and the player sees the reply within 2 seconds without reloading.
