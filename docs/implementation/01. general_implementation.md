How to build the platform described in `docs/architectural design/01. general_design.md`. The module guides (`02` to `06`) build on this file, so read it first. Moving the WordPress data is in `docs/migration/wordpress_data_migration.md`.

**Rules that apply to every task**
- Follow `.kiro/steering/development-workflow.md` for branches, commits, secrets and deployment.
- This is Next.js 16. Before writing code that touches routing, caching, Server Actions or `proxy.ts`, read the matching guide in `node_modules/next/dist/docs/` (see section 4). Do not copy patterns from older Next.js tutorials.
- Requirement ids (GEN-x.y, PLR-x.y, …) and design sections are quoted in code comments only where a rule would otherwise look arbitrary.
- If this guide and the design disagree, the design wins. Stop and ask before guessing.

## 2. Local development set-up

1. Install Node with nvm for Windows: `nvm install 24.22.3`, then `nvm use 24.22.3`. Check with `node -v`.
2. Install Docker Desktop. Docker runs PostgreSQL locally and in tests.
3. `npm ci`
4. Copy `.env.example` to `.env.local` and fill in the values (section 6). Ask the project owner for test keys (Stripe test mode, SMTP2GO sandbox, Kit, Google, reCAPTCHA).
5. Start the database: `docker compose -f compose.yaml -f compose.local.yaml up -d db`
6. Create the schema: `npx prisma migrate dev`
7. Seed reference data and plans: `npm run db:seed`
8. Run the three processes, each in its own terminal:
   - `npm run dev` (Next.js, port 3000)
   - `npm run dev:realtime` (WebSocket server, port 3001)
   - `npm run dev:worker` (outbox and scheduled jobs)
9. Stripe webhooks locally: `stripe listen --forward-to localhost:3000/api/stripe/webhook`, and put the printed secret in `.env.local` as `STRIPE_WEBHOOK_SECRET`.

`compose.local.yaml` can also run all services in containers (`docker compose -f compose.yaml -f compose.local.yaml up`), which is how you check the production set-up on your own machine.

## 7. Database

### 7.1 Prisma set-up

- `prisma/schema.prisma` is replaced in full by the models in design files `01` to `06`. The current schema has no production data and no migrations, so start fresh.
- Generator: `provider = "prisma-client"`, `output = "../src/generated/prisma"`. Import the client from `@/generated/prisma/client`. Check the Prisma 7 docs for the exact generator options of the installed version.
- The driver adapter `@prisma/adapter-pg` is used, as in the current `src/lib/db.ts`.
- Every model follows `01` design section 4:
  - `id String @id @default(uuid(7)) @db.Uuid`, except slug-keyed reference tables and `Country`
  - foreign keys `@db.Uuid`
  - `createdAt DateTime @default(now())`, `updatedAt DateTime @updatedAt`, `createdById String? @db.Uuid`, `updatedById String? @db.Uuid` (append-only tables: `createdAt` and `createdById` only)
  - Boolean fields named `is…` or `has…`
- Write relations with explicit `onDelete`. Default to `Restrict`; use `Cascade` only for child rows that mean nothing without their parent (for example `ClubHistory`, `OfferSkill`).

### 7.2 Migrations

- Create migrations with `npx prisma migrate dev --name <what-changed>`. Commit the generated folder.
- Anything Prisma cannot express goes in the same migration's `migration.sql`, added by hand with `npx prisma migrate dev --create-only` first:
  - `CREATE EXTENSION IF NOT EXISTS pg_trgm; CREATE EXTENSION IF NOT EXISTS unaccent;` (first migration)
  - partial unique indexes (one current membership per manager, one paid and one trial subscription per organisation)
  - check constraints (offer fields required unless draft; club/union/institution text-or-id fields)
  - trigram indexes (`USING gin (… gin_trgm_ops)`) and GIN indexes on arrays
  - grants (section 7.3)
- Never edit a migration that has been merged into `dev`. Add a new one.
- Production applies migrations with `npx prisma migrate deploy` (never `migrate dev`).

### 7.3 Database roles

Created once per database by `docker/postgres/init/01-roles.sql` (and by hand on an existing database):

| Role | Rights |
|---|---|
| `offload_owner` | Owns the schema; runs migrations |
| `offload_app` | `SELECT, INSERT, UPDATE, DELETE` on all tables, except: no `UPDATE`/`DELETE` on `"AuditEvent"` and `"Message"` |
| `offload_realtime` | `SELECT` on `"Session"`, `"User"`, `"OrganisationMember"`, `"ConversationParty"` only |
| `offload_retention` | `SELECT, DELETE` on `"AuditEvent"` |

Each migration that adds a table ends with the `GRANT` lines for it. `DATABASE_URL` uses `offload_app`; migrations use `offload_owner` through `prisma.config.ts` reading `DATABASE_URL_OWNER` locally and in the deploy step.

### 7.4 Actor columns

`createdById` and `updatedById` are filled automatically:
- `src/server/context.ts` holds an `AsyncLocalStorage<{ actorId: string | null }>`.
- `runAsUser(userId, fn)` and `runAsSystem(fn)` set it. Server Actions and Route Handlers wrap their work in `runAsUser(viewer.user.id, …)`. Jobs, webhooks and the migration use `runAsSystem` (actor `null`, shown as "System").
- A Prisma client extension in `src/server/db.ts` adds `createdById`/`updatedById` to every `create`, `createMany`, `update`, `updateMany` and `upsert` from the current context. A unit test checks that an update inside `runAsUser` sets `updatedById`.

### 7.5 Transactions

- Every service that writes more than one row uses `prisma.$transaction(async (tx) => { … })` and passes `tx` to helpers (`audit(tx, …)`, `enqueue(tx, …)`, `notifyRealtime(tx, …)`).
- Row locks for guards (`assertNotLastVerifiedManager`, `assertNotLastAdministrator`, billing changes) use `tx.$queryRaw\`SELECT id FROM "Organisation" WHERE id = ${id} FOR UPDATE\``.
- Raw SQL always uses tagged templates (`$queryRaw\`…${value}\``), never string concatenation.

### 7.6 Seeding

`prisma/seed.ts` is idempotent: it upserts by id or slug, so it can run on every deploy. It seeds countries (from `i18n-iso-countries`, English names), positions, skills, qualifications, leagues, industries and default settings. Plans are seeded from the JSON file printed by the Stripe setup script (`06` section 3).

## 8. Authentication (Better Auth)

`src/server/auth.ts` creates one Better Auth instance. `src/app/api/auth/[...all]/route.ts` exports its handlers with `toNextJsHandler(auth)`. Read the Better Auth docs for the installed version before writing this; option names below are the intent.

**Configuration**

| Area | Setting |
|---|---|
| Database | Prisma adapter, `provider: 'postgresql'`. `advanced.database.generateId: false`, so Prisma's `uuid(7)` default creates ids. |
| Models | Map the core models onto ours: `user` → `User` (with `emailVerified` mapped to `isEmailVerified`), `session` → `Session`, `account` → `Account`, `verification` → `Verification` |
| User fields | Declare `role`, `status`, `firstName`, `lastName`, `documentStatus` and the other platform fields as `additionalFields` with `input: false`, so nobody can set them through Better Auth's endpoints |
| Email and password | Enabled; `minPasswordLength: 8`, `maxPasswordLength: 50`; `autoSignIn: true` after sign-up; `revokeSessionsOnPasswordReset: true`; reset token lifetime 1 hour |
| Passwords | `password.hash` and `password.verify` call our functions (section 8.2) |
| Email verification | `sendOnSignUp: true`, lifetime 48 hours; `sendVerificationEmail` enqueues the email and also sends it at once with `after()` |
| Change email | Enabled; the link goes to the new address; `pendingEmail` is set when requested and cleared when used |
| Sessions | `expiresIn: 365 days`, `updateAge: 1 hour`, `cookieCache.enabled: false` |
| Rate limit | Enabled with custom storage backed by our `RateLimit` table (section 13) |
| Plugins | `captcha({ provider: 'google-recaptcha', secretKey, minScore: 0.5 })` for sign-up, sign-in and password reset; `nextCookies()` so Server Actions can set cookies |

**Rules**
- The full password rules (upper case, lower case, number, symbol) are checked by the zod schema in the Server Action before calling Better Auth, and again in a `before` hook on sign-up and reset, so the endpoints cannot be used to skip them.
- Registration is a Server Action: validate → check the honeypot → call `auth.api.signUpEmail` → create the `PlayerProfile` or organisation membership in a `databaseHooks.user.create.after` hook inside the same transaction where the adapter allows it; otherwise in the action, and delete the user if that fails.
- **Lockout (GEN-4.3):** a `before` hook on `/sign-in/email` refuses when `lockedUntil > now()` with "Too many attempts. Try again in 15 minutes." An `after` hook increments `failedLogins` on failure (locking for 15 minutes at 5 failures within 15 minutes) and resets it on success.
- **Suspended users:** a `databaseHooks.session.create.before` hook refuses to create a session for a user whose status is not `ACTIVE`. Suspending a user deletes their sessions.
- **Staff invitation** uses our own `Token` table (`05`), then sets the password with `auth.api` admin-safe calls on the server.

### 8.1 `getViewer()`

`src/server/dal/viewer.ts`:
1. `const session = await auth.api.getSession({ headers: await headers() })`
2. If there is none, or the user is not `ACTIVE`, return `null`.
3. Load the membership, organisation, `hasActiveSubscription` and staff permissions in one query batch.
4. Return `{ user, role, isVerified, isStaff, membership, organisation, entitlements, permissions, mustAcceptTerms }`.

It is wrapped in React `cache()`, so it runs once per request.

### 8.2 Password hashing

`src/server/auth/passwords.ts`:
- `hashPassword(plain)`: Argon2id, `memoryCost: 19456` (19 MiB), `timeCost: 2`, `parallelism: 1`. The result already starts with `$argon2id$`.
- `verifyPassword({ hash, password })`:
  - `$argon2id$…` → `argon2.verify`.
  - `wp-phpass$<setting>$<argon2 hash>` → compute the phpass hash of `password` with `<setting>` (salt and rounds from the `$P$B…` prefix), then `argon2.verify` it against `<argon2 hash>`. On success, an after-sign-in hook replaces the stored value with `hashPassword(password)`.
  - Anything else → `false`.
- The phpass algorithm is implemented in `src/server/auth/phpass.ts` (about 40 lines: MD5 iterated `2^n` times, custom base-64). Unit tests use hashes generated for this purpose, never real user hashes.

## 9. Email, notifications and the outbox

### 9.1 Outbox

- `OutboxMessage`: `id, type, payload Json, status (PENDING | SENT | FAILED), attempts, nextAttemptAt, lastError, createdAt`.
- `enqueue(tx, type, payload)` validates `payload` against the zod schema registered for `type` and inserts a row in the caller's transaction.
- Types: `email.send`, `newsletter.subscribe`, `newsletter.unsubscribe`, `image.process`, `export.user-data`, `export.users-csv`.

### 9.2 Email types

`src/server/email/types.ts` lists every email type with its SMTP2GO template id and allowed variables:

```ts
export const emailTypes = {
  'auth.verify-email':  { templateId: 'tpl_…', variables: ['firstName', 'link'] },
  'message.new':        { templateId: 'tpl_…', variables: ['firstName', 'senderName', 'link'] },
  // …one entry per email in the designs
} as const
```

- `sendEmail(tx, { type, to, variables })` checks that the variable names match exactly, then enqueues `email.send`.
- Template ids live in this file, not in the environment. The SMTP2GO templates themselves are created in SMTP2GO by the project owner; this file is the list of what must exist.
- Text that users wrote (message bodies, notes, document names) is never a variable.

### 9.3 Notifications

`notify(tx, { userIds, type, linkPath, subjectName })` inserts `Notification` rows and publishes `notification.created` over realtime (section 11). For organisations, `userIds = await managersToNotify(tx, orgId)`.

### 9.4 Outbound safety switch

`OUTBOUND_MODE` protects real people while the platform runs with imported data before launch:

| Mode | Emails | Kit | Used |
|---|---|---|---|
| `redirect` | Every email goes to `OUTBOUND_REDIRECT_EMAIL`, with the real recipient added to the subject | No calls | Local development, testing with migrated data, production before go-live |
| `live` | Sent to the real recipient | Calls made | Production after go-live |

The default is `redirect`. The worker logs the mode at start-up. Stripe is controlled separately by using test keys until go-live.

### 9.5 SMTP2GO and Kit webhooks

- `POST /api/webhooks/smtp2go?secret=…`: compare the secret with `SMTP2GO_WEBHOOK_SECRET` using a constant-time comparison. On `bounce` (hard) or `spam` events, set `User.isEmailUndeliverable = true` and alert staff.
- `POST /api/webhooks/kit`: check `KIT_WEBHOOK_SECRET` the same way. On `subscriber.unsubscribed`, set `isNewsletterOptedIn = false` for that email.

## 10. Worker

`worker/index.ts` runs two loops in one process:

1. **Outbox loop**, every 2 seconds:
   ```sql
   SELECT * FROM "OutboxMessage"
   WHERE status = 'PENDING' AND "nextAttemptAt" <= now()
   ORDER BY "createdAt" LIMIT 20
   FOR UPDATE SKIP LOCKED
   ```
   Run each handler; on success set `SENT`; on failure increase `attempts`, set `nextAttemptAt = now() + 2^attempts minutes`, and after 8 attempts set `FAILED` and alert staff.
2. **Job schedule** with `croner` (`timezone: 'Europe/London'`). Each job calls `POST http://web:3000/api/jobs/<job>` (locally `http://localhost:3000`) with header `Authorization: Bearer ${JOB_SECRET}`:

| Job | Schedule |
|---|---|
| `offer-expiry` | every hour at minute 5 |
| `unverified-accounts` | daily 03:00 |
| `staff-summary` | daily 08:00 |
| `billing` | daily 09:00 |
| `billing-reconciliation` | daily 04:00 |
| `newsletter-sync` | daily 05:00 |
| `audit-retention` | daily 02:00 (runs in the worker with `DATABASE_URL_RETENTION`) |
| `cleanup` | daily 02:30 |
| `billing-retention` | 1 January 04:30 |

- `src/app/api/jobs/[job]/route.ts` checks the secret, looks the job up in `src/server/jobs/index.ts`, and runs it inside `runAsSystem`. An unknown job returns 404.
- Every job is safe to run twice (it works from the current state, not from "since last run").
- `proxy` (Caddy) blocks `/api/jobs/*` from outside.

## 11. Realtime server

## 12. Files

### 12.1 Upload purposes

`src/lib/constants.ts`:

| Purpose | Formats | Max size | Bucket area | Variants |
|---|---|---|---|---|
| `PROFILE_PICTURE` | JPEG, PNG, WebP, HEIC, AVIF | 2 MB | `public/` | avatar 128, card 400, header 1200 |
| `ORGANISATION_LOGO` | same | 2 MB | `public/` | avatar 128, card 400, header 1200 |
| `COACH_IMAGE` | same | 2 MB | `public/` | avatar 128, card 400 |
| `IDENTITY_DOCUMENT` | PDF and the image formats | 10 MB | `private/` | one full-size WebP for images |
| `ORGANISATION_DOCUMENT` | PDF and the image formats | 10 MB | `private/` | same |
| `CV` | PDF | 10 MB | `private/` | none |

### 12.2 Flow

1. The upload field calls `POST /api/uploads` with `{ purpose, contentType, size }`. The handler checks the viewer, the purpose rights and the limits, creates a `File` row (`PENDING`), and returns a V4 signed `PUT` URL for `offload-uploads/<fileId>` valid 10 minutes, with the content type and `x-goog-content-length-range: 0,<max>` signed in.
2. The browser `PUT`s the file to that URL with the same headers.
3. The browser calls `PUT /api/uploads` with `{ fileId }`. The handler enqueues `image.process` (or `document.process` for PDFs) and returns.
4. The worker (`worker/images.ts`):
   - downloads the object and reads its first bytes to detect the real type (magic numbers); a type that is not allowed for the purpose → `REJECTED`
   - images: decode HEIC with `heic-decode`, then `sharp(…).rotate()` (applies orientation), strip metadata, `.webp({ quality: 82 })` for each variant (`quality: 90`, full size, for documents)
   - PDFs: copied as they are
   - writes to `offload-user-content` under `public/<fileId>/<variant>.webp` or `private/<fileId>.<ext>`, deletes the upload, sets `READY`, and links the file to its owner record only now
5. The field polls `GET /api/uploads?fileId=` every second for up to 30 seconds and shows the result.

### 12.3 Reading

- `GET /media/[fileId]/[variant]`: public images (logos, coach images) for anyone; profile pictures for signed-in users. Redirect (302) to a signed `GET` URL valid 1 hour, with `Cache-Control: private, max-age=3000`.
- `GET /files/[fileId]`: checks the policy for the file's purpose, writes an audit event for identity documents, redirects to a signed URL valid 5 minutes with `Cache-Control: private, no-store`.
- Missing images show the placeholder from `src/components/ui/placeholder-image.tsx`.

## 13. Security

- **Rate limits:** `src/server/rate-limit.ts` with a `RateLimit` table (`key, windowStart, count`), using `INSERT … ON CONFLICT DO UPDATE SET count = count + 1 RETURNING count`. Limits live in `src/lib/constants.ts` so they are easy to find:

| Key | Limit |
|---|---|
| sign-in per IP / per email | 20 per 15 min / 5 per 15 min (lockout) |
| registration per IP | 5 per hour |
| password reset per email | 3 per hour |
| verification resend per user | 3 per hour (GEN-3.4) |
| messages per user | 30 per hour, 200 per day |
| uploads per user | 30 per hour |
| contact form per IP | 5 per hour |

- **Honeypot:** a visually hidden `website` field on the four protected forms. If it is filled in, return the same success-looking response and do nothing.
- **reCAPTCHA v3:** the form loads the script only on these pages, runs `grecaptcha.execute(siteKey, { action })` on submit and sends the token. Better Auth's captcha plugin checks sign-up, sign-in and reset; `src/server/integrations/recaptcha.ts` checks the contact form (score ≥ 0.5, matching action).
- **Security headers** (`proxy.ts`): `Content-Security-Policy` with a per-request nonce, allowing only `'self'`, the Google domains for Maps, Places and reCAPTCHA, `js.stripe.com` where needed, and the GlitchTip host; `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`; `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; `frame-ancestors 'none'`.
- **Logs** never include emails, tokens, cookies, document names or message bodies. Use the logger in `src/server/log.ts`, which drops those keys.

### 16.2 Server Action

```ts
'use server'
export async function updatePlayingInfo(_prev: FormState, formData: FormData): Promise<FormState> {
  const viewer = await getViewer()
  if (!viewer) redirect('/login')
  const parsed = playingSchema.safeParse(formToObject(formData))
  if (!parsed.success) return { status: 'error', fieldErrors: parsed.error.flatten().fieldErrors }
  if (!canEditOwnPlayerProfile(viewer)) return { status: 'error', message: 'You cannot edit this profile.' }
  await runAsUser(viewer.user.id, () => playerService.updatePlaying(viewer.user.id, parsed.data))
  updateTag(`player:${viewer.user.id}`)
  return { status: 'ok', message: 'Saved' }
}
```

- Actions never import the Prisma client. Services never read cookies or headers.
- Known failures (validation, policy, guard refusals) return `{ status: 'error' }` with the message from the requirements. Unexpected errors are thrown, logged and shown as "Something went wrong. Please try again."
- Guards in services throw `DomainError(code, message)`; actions catch `DomainError` only.

### 16.3 Gated page

```tsx
export default async function PlayersPage({ searchParams }: { searchParams: Promise<Record<string, string | string[]>> }) {
  const viewer = await getViewer()
```

### 16.4 Infinite loading

- The page renders the first 24 results on the server.
- `<InfiniteList>` (client) watches a sentinel element with `IntersectionObserver` and calls a Server Action `loadMore(filters, cursor)` that returns the next 24 and the next cursor.

## 17. Design system and styling

One set of design tokens drives the whole platform. Changing a token in one place changes it everywhere.

**Starting point:** the design is copied from the live WordPress site, not from the code currently in this repository. The current `globals.css`, components and pages are a throw-away prototype: their colours, fonts and layouts are not reused. Token values come from the WordPress Elementor global settings (17.2) and each screen's layout from the Elementor export in `wp-db-export/elementor-export/` (read with `node ee.mjs outline <file>` in `wp-db-export/`).

### 17.1 Rules

1. **No raw design values in code.** Colours, font families, font sizes, font weights, line heights, letter spacing, spacing (padding, margin, gap), sizes, border widths, border radius, shadows, z-index, breakpoints, transition durations and easing all come from tokens. This applies to Tailwind classes, `.module.scss` files and any other CSS.
   - Not allowed: `#D4782F`, `rgb(…)`, `16px`, `1.5rem`, `font-weight: 700`, `z-index: 50`, Tailwind arbitrary values such as `p-[13px]`, `text-[#333]`, `rounded-[6px]`.
   - Allowed raw values: `0`, `100%`, `auto`, `inherit`, `currentColor`, `transparent`, `none`, and `1fr`-style grid fractions.
2. **No inline styles.** The `style` prop is not used. First look for a way without it (for example the native `<progress>` or `<meter>` element for the profile completeness bar). The only exception is passing a truly dynamic value as a CSS custom property, `style={{ '--offset': value }}`, read in the module as `var(--offset)`. Each exception has an `eslint-disable-next-line` comment with the reason.
3. **Where styles go:**
   - Layout and simple styling: Tailwind utility classes, which are generated from the tokens (17.2).
   - Anything more than a few utilities, states (`:hover`, `:focus-visible`, `[data-selected]`), media queries, pseudo-elements or repeated combinations: a CSS module next to the component, `component-name.module.scss`, imported as `styles` and combined with Tailwind classes through `cn()`:
     ```tsx
     import styles from './player-card.module.scss'
     <article className={cn(styles.card, 'flex flex-col gap-md')}>
     ```
   - Global CSS is only `src/app/globals.css` (tokens, base element styles, fonts). No other global stylesheets.
4. **Tokens only through variables.** In `.module.scss` use `var(--color-accent)`, `var(--spacing-md)`, `var(--radius-pill)`, `var(--text-base)`. Do not copy token values into Sass variables.
5. **Text always uses a text style** (17.3), such as `text-h2` or `text-body`. Font family, size, weight, line height and letter spacing are not set one by one in components.
6. **Responsive:** mobile first, using the breakpoint tokens (`md`, `lg`) through Tailwind prefixes or the Sass mixin in `src/styles/_breakpoints.scss`, which reads the same values.
7. **A value the WordPress site uses but the tokens lack** is added as a new token in `globals.css` first, then used. Never write it inline "just once".

## 18. Reusable code

### 18.1 Rules

1. **Look before you build.** Before writing a component, hook or helper, search `src/components`, `src/hooks` and `src/lib` (and the catalogue in 18.4) for one that already does the job. Extend it with a prop or variant rather than writing a near copy.
2. **Extract on the second use.** When markup, logic or a style block appears a second time, move it into a shared component, hook or helper and use it in both places. Do not wait for the third copy.
3. **One job per unit.** A component renders one thing; a hook manages one piece of state or one effect; a helper does one calculation. A file over about 200 lines is a sign it should be split.
4. **Business rules live once.** A rule such as "contract ending soon", "can this viewer apply", the age calculation or price formatting has exactly one function, used by every page, email and job that needs it.

5. **Data and UI are separate.** Data is loaded and changed in one layer, and shown in another:

| Layer | Lives in | Does | Never does |
|---|---|---|---|
| Route files (`page.tsx`, `layout.tsx`) | `src/app/` | Read params, call `getViewer()`, the policy and DAL functions, pick the gate, pass plain data to components | Markup beyond arranging components; styling |
| Server Actions | `src/actions/` | Parse input, check viewer and policy, call a service, refresh cache tags | Query the database directly; return database rows unfiltered |
| DAL and services | `src/server/` | All database reads (DAL) and writes (services), with explicit field selections | Import React or components |
| Components | `src/components/` | Render the props they are given; call Server Actions passed in or imported for user actions | Import anything from `src/server/`, call `getViewer()`, query data, or know where data comes from |
| Hooks | `src/hooks/` | Client state and effects (realtime, infinite loading, debouncing) | Fetch with `fetch()` to our own API; Server Actions are used instead |

- Components receive data shaped for display (view models such as `PlayerCardData`), defined next to the DAL function that produces them, not Prisma model types.
- An ESLint `no-restricted-imports` rule blocks `@/server/*` imports in `src/components/` and `src/hooks/`.

### 18.3 How to write a component

- **Files:** kebab-case names (`player-card.tsx`, `player-card.module.scss`), one exported component per file, named export (`export function PlayerCard`). Each folder has an `index.ts` that re-exports its public components.
- **Props:** a typed `Props` interface. Primitives pass through native attributes (`...rest`) and accept `className`, merged last with `cn()` so callers can add layout classes.
- **Variants:** a `variant` and `size` prop with a fixed set of values (for example `variant: 'primary' | 'secondary' | 'ghost' | 'danger'`), mapped to classes in one object inside the component. No one-off colour props.
- **Server first:** components are Server Components by default. Add `'use client'` only to the smallest piece that needs state, effects or browser APIs, and pass server data down as props.
- **Composition over options:** prefer children and slots (`<Card><Card.Header/>…</Card>`) to long lists of boolean props.
- **Accessibility built in:** primitives use `react-aria-components` where they are interactive, so keyboard use, focus rings and ARIA roles come for free. Every input has a visible label; icon-only buttons have `aria-label`; focus styles use `--color-focus`.
- **Text:** user-facing strings that appear in more than one place (error messages from the requirements, gate texts, empty states) live in `src/lib/messages.ts` and are imported, never retyped.
- **Icons:** one icon set, `lucide-react` (ISC), through a wrapper `Icon` component that sets the size from the tokens.
- **Images:** `next/image`, or the `/media/…` URL through `UserAvatar` and `OrganisationLogo`, which handle the placeholder.

### 18.4 Component catalogue

`src/components/README.md` lists every shared component with one line on what it is for and its main props. Adding or changing a shared component updates this list in the same commit. A development-only page `/dev/components` (not built in production) shows each primitive in its variants, so it is easy to see what exists.

## 19. Other code rules

| Area | Rule |
|---|---|
| TypeScript | `strict` on; no `any` (use `unknown` and narrow); no `@ts-ignore` (use `@ts-expect-error` with a reason); exported functions have explicit return types |
| Naming | Components `PascalCase`; functions and variables `camelCase`; constants `UPPER_SNAKE_CASE`; files kebab-case; booleans `is…`/`has…`/`can…` |
| Magic values | Limits, page sizes, durations and route paths live in `src/lib/constants.ts` and `src/lib/routes.ts`. Links use `routes.player(id)` rather than typed strings. |
| Dates and money | Always through `formatDate`, `formatDateTime`, `formatRelative` and `formatMoney`. Never `toLocaleString` in components. Store UTC; show Europe/London. |
| Data access | Data and UI are separate layers (section 18.1, rule 5). No database or secret access outside `src/server/`. |
| Errors | No empty `catch`. Catch only what you can handle; let the rest reach the error boundary and GlitchTip. |
| Logging | Use `src/server/log.ts`; no `console.log` in committed code (ESLint `no-console`). |
| Imports | Absolute `@/…` imports across folders; relative only within a folder. Import order enforced by ESLint. No circular imports between modules (services call each other only through exported service functions). |
| Dependencies | Before adding a package: check it is maintained, its licence (MIT, Apache-2.0, BSD, ISC) and its size; prefer an existing dependency; note it in section 5 in the same commit. |
| Comments | Explain why, not what. Reference the requirement id where a rule looks arbitrary. No commented-out code. |
| Accessibility | WCAG 2.2 AA: colour contrast checked against the tokens, keyboard reachable, visible focus, form errors linked to fields with `aria-describedby`, `lang="en-GB"`. Axe runs in end-to-end tests. |
| Performance | Images sized through the variants; heavy client libraries (Tiptap, Recharts, Maps) loaded with `next/dynamic` only where used; no client component above the page's interactive parts. |
| Security | Never trust client input; validate with zod in the action; never render user HTML except the sanitised descriptions; never put secrets in `NEXT_PUBLIC_` variables. |
| Tests | Every shared helper and hook has unit tests; every shared component used in forms has a rendering test for its error and disabled states. |

## 20. Docker and deployment

### 20.1 Images

All three Dockerfiles are multi-stage, based on `node:24.22.3-bookworm-slim`, run as the non-root `node` user, and copy only what they need:
- `web.Dockerfile`: `next build` with `output: 'standalone'` in `next.config.ts`; the final stage copies `.next/standalone`, `.next/static` and `public`, and runs `node server.js`.
- `realtime.Dockerfile` and `worker.Dockerfile`: build with `tsc` (or `tsx` bundling) into `dist/`, run `node dist/…`. The worker image installs `sharp` for `linux-x64`.

### 20.2 Compose files

| File | Contains |
|---|---|
| `compose.yaml` | Services `web`, `realtime`, `worker`, `db`, each with health checks, `restart: unless-stopped`, internal network only |
| `compose.local.yaml` | `db` publishes `5432` on `127.0.0.1`; source mounted; dev commands; uses `.env.local` |
| `compose.prod.yaml` | Images `europe-west2-docker.pkg.dev/<project>/offload/<service>:${IMAGE_TAG}`; adds `proxy` (Caddy, ports 80 and 443), `backup` (pgBackRest), `glitchtip`; uses `.env.prod` |

Production commands on the VM: `docker compose -f compose.yaml -f compose.prod.yaml --env-file .env.prod …`.

### 20.3 Caddy

`docker/Caddyfile`: `offloadagency.com` with automatic HTTPS; `handle /ws*` → `realtime:3001`; `handle /api/jobs/*` → `respond 404`; everything else → `web:3000`; `errors.offloadagency.com` → `glitchtip:8000`; `www.` redirects to the bare domain.

### 20.4 GitHub Actions

`ci.yml` (pushes to `dev`, `feature/**`, `fix/**`, and pull requests):
1. checkout, `actions/setup-node` with `.nvmrc` and npm cache
2. `npm ci`
3. `npx prisma validate` and `npx prisma generate`
4. `npm run format:check`, `npm run lint`, `npm run lint:styles`, `npm run typecheck`
5. `npm test`
6. start a `postgres:16` service container, `npx prisma migrate deploy`, `npm run test:integration`
7. `npm run build`

`deploy-production.yml` (push to `main`): the same checks, then build and push the three images tagged with `${{ github.sha }}`, authenticate to Google Cloud with Workload Identity Federation, SSH to the VM using the `PROD_*` secrets, write `IMAGE_TAG`, `docker compose pull`, run `npx prisma migrate deploy` and `npm run db:seed` in a one-off `web` container, `docker compose up -d`, check `/api/health` for 60 seconds, and redeploy the previous tag on failure.

The agent does not run or change these workflows unless asked (steering guide).

## 23. Definition of done (every task)

- The requirement ids it covers are listed in the pull request.
- Every new page, Server Action and Route Handler checks the viewer and a policy on the server.
- Validation messages match the requirements text.
- Unit and integration tests for the new rules; an end-to-end test for any new user journey.
- No raw design values, no inline styles, no duplicated markup or logic; shared pieces are in the right folder and listed in the catalogue (sections 17 to 19).
- `format:check`, `lint`, `lint:styles`, `typecheck`, tests and `build` pass.
- No personal data in logs, fixtures or commits.
- Docs updated if the behaviour differs from the design (after asking).
