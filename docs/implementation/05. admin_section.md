## 2. Menu and permissions

- `src/server/policies/staff.ts`:
  ```ts
  export const PERMISSIONS = {
    ADMINISTRATOR: ['stats.view', 'verification.review', 'users.view', …, 'staff.manage', 'users.changeRole', 'settings.manage', 'plans.manage'],
    OFFLOAD_ADMIN: ['stats.view', 'verification.review', 'users.view', …],
  } as const satisfies Record<StaffRole, readonly Permission[]>
  export const hasPermission = (v: Viewer, p: Permission) => v.permissions.has(p)
  export async function requirePermission(p: Permission) { … }   // throws notFound() when missing
  ```
  The two lists copy design section 4.1 exactly.
- `src/components/dashboard/menu.ts`: an array of `{ label, href, show(viewer) }`, so each item has one visible rule. Items whose condition is not met but should be visible (verification, subscription) link to a page that shows the gate (ADM-1.6).
- Menu counts for staff: one grouped query per request (`SELECT subject, organisationType, count(*) … WHERE status = 'PENDING' GROUP BY …`).
- Tests: every permission × both staff roles; no permission name contains `offer.edit`, `application`, or `message.read` (a test greps the permission list).

## 3. Account settings

`/dashboard/settings`, one form per item:

| Item | Implementation |
|---|---|
| Change email | Better Auth change-email (`01` section 8); shows the pending address and "Resend link" |
| Change password | Current and new password; Better Auth `changePassword` with `revokeOtherSessions: true` |
| Sign out of all devices | Better Auth `revokeSessions`, then redirect to `/login` |
| Newsletter | Toggle; updates `isNewsletterOptedIn` and enqueues the Kit call |
| Download my data | Enqueues `export.user-data`; message "We'll email you a link within an hour" |
| Delete my account | Dialog asking for the password and typing "DELETE"; runs `deleteAccount`; guards return their messages |

## 4. Verification

### 4.1 Lists

- One DAL function `listVerificationQueue({ subject, organisationType, search, sort, cursor })` on `VerificationRequest` with `status = 'PENDING'`, joined to the user or organisation for the display columns.
- Columns: name, email (staff only), role or organisation type, submitted date, possible duplicate flag, link to review.
- Sort: oldest first by default; by name. Search: name or email.
- Empty: "Nothing to review".
- Tables use `@tanstack/react-table` in `src/components/dashboard/data-table.tsx` (sorting and selection only; data comes from the server, paged by cursor with "Next" / "Previous").

### 4.2 Review page

`/dashboard/staff/review/[requestId]`:
- The person's or organisation's details, any earlier decisions, the possible duplicate with a link.
- Documents through `/files/<id>`: images in `<img>`, PDFs in `<iframe>` (`sandbox` attribute, no scripts). Opening is audited by the files route.
- Buttons: Approve, Reject (reason required, ≤ 500 characters), and for verified subjects Revoke (reason required).

### 4.3 Decision services

`src/server/services/verification/decide.ts`, each in one transaction with `requirePermission('verification.review')` and an audit event:

| Function | Effect |
|---|---|
| `approvePlayer(requestId)` | request `APPROVED`; `documentStatus = VERIFIED`, `documentDecidedAt/ById`; `listPlayer`; notify the player |
| `approveManager(requestId)` | request `APPROVED`; `documentStatus = VERIFIED`; membership `ACTIVE`; notify |
| `approveOrganisation(requestId)` | request `APPROVED`; organisation `PUBLISHED`, `publishedAt`; notify managers; `updateTag('org:' + id)` |
| `reject(requestId, reason)` | request `REJECTED` with reason; user `documentStatus = REJECTED` or organisation `REJECTED` (or claim membership `REJECTED`); notify with the reason |
| `revokeUser(userId, reason)` | `documentStatus = REVOKED`; players `unlistPlayer`; managers membership `REMOVED` after `assertNotLastVerifiedManager` |
| `decideChange(changeRequestId, approve, reason?)` | apply or discard the values (`03` section 8); new slug if the name changed |
| `bulkApprove(requestIds)` | at most 50 ids (zod `max(50)`); loops calling the matching approve function, each in its own transaction; returns `{ id, ok, error? }[]` shown per row |

## 5. Users

- **List:** filters role, organisation type, verification state, joined date range, country (nationalities overlap), status; search by name or email; CSV export button.
- **Detail:** profile fields, verification history, organisation membership, applications count, message count (counts only), audit timeline.
- **Edit:** the users' own schemas plus staff-only fields (email, names, date of birth). Changes apply at once and are audited with old and new values. A staff edit never changes `documentStatus`.
- **Suspend / reactivate:** reason required; `status = SUSPENDED`, sessions deleted, `session.revoked` published, players unlisted, open applications withdrawn (`04`); reactivation reverses the listing. Guarded for the last verified manager and the last Administrator.
- **Delete:** `deleteAccount` with the same guards.
- **Send password reset link:** Better Auth `requestPasswordReset` for that email.
- **CSV export (ADM-7.6):** enqueues `export.users-csv` with the current filters; the worker writes `private/exports/<id>.csv` (UTF-8 with BOM so Excel opens it), and staff get a notification with a `/files/<id>` link valid 1 hour. Columns: name, role, organisation type, email, verification state, newsletter opt-in.

## 6. Organisations

- **List:** filters type, status, country, subscription status; search by name.
- **Detail:** all fields, managers (with "Remove manager"), subscription summary, offers and applications counts, audit timeline.
- **Edit:** any field, any status, applied at once and audited.
- **Unpublish / republish / delete:** call the `03` lifecycle services; unpublish and delete ask for a reason and confirmation.

## 7. Offer moderation

`/dashboard/staff/offers/[id]` shows the public offer page content only. "Close for breaking the terms" asks for a reason and calls `closeForViolation` (`04`). No other offer action exists for staff.

## 8. Staff accounts

- **Invite:** Administrator enters name, email and role (`OFFLOAD_ADMIN` or `ADMINISTRATOR`). The service creates the `User` (`isEmailVerified` false until accepted), a `Token(STAFF_INVITE)` valid 7 days (store the SHA-256 of a 32-byte random token), and emails the link `/accept-invite?token=…`.
- **Accept:** the page checks the token, asks for a password (same rules), sets it through Better Auth's server API, marks the token used, sets `isEmailVerified`, `emailVerifiedAt`, and signs the user in.
- **Promote an existing user:** stores `previousRole`, sets the staff role, deletes the user's sessions. "Return to previous role" reverses it. Both need `users.changeRole`.
- **Remove staff:** returns them to `previousRole` or suspends them. All role changes and removals run `assertNotLastAdministrator` (locks Administrator rows, counts the others).

## 9. Statistics

`/dashboard` for staff (needs `stats.view`):
- Counts with `COUNT(*) FILTER (WHERE …)` per entity, run with `Promise.all`.
- Weekly registrations for the last 12 weeks by role: `date_trunc('week', "createdAt")`, shown with a Recharts bar chart in a client component.
- Billing figures from `06` (`billingStats()`).
- Each figure links to the matching filtered list.

## 10. Audit log

- `src/server/audit.ts`:
  ```ts
  const auditFields = {
    'verification.approve': ['requestId', 'subject'],
    'message.sent': ['conversationId', 'senderPartyKey', 'recipientPartyKey'],
    // …one entry per action type
  } satisfies Record<AuditAction, readonly string[]>
  export async function audit(tx: Tx, e: { action: AuditAction; subjectType: string; subjectId: string; data?: Record<string, unknown>; before?: …; after?: …; relatedUserIds?: string[]; relatedOrgId?: string }) { … }
  ```
  It rejects keys not listed for the action, reads the actor from the context (`actorKind`, `actorId`, `systemActor` such as `job:billing`), and stores the request IP when there is one.
- `before`/`after` store only the changed fields, never `password`, `token`, `body` or file names (unit test).
- **Search:** user, organisation, action prefix, date range; cursor paging.
- **Timelines:** on user and organisation detail pages: `actorId = X OR X = ANY("relatedUserIds") OR "relatedOrgId" = X`, newest first.
- **Retention job** (`audit-retention`, worker, `DATABASE_URL_RETENTION`): delete events older than 2 years, except actions starting with `billing.` or `subscription.`, which are deleted after 6 years. Deletes in batches of 1,000.

## 11. Settings, terms and support

- `Setting` rows: `email.fromName`, `email.fromAddress`, `support.email`, `terms.version`, `terms.updatedAt`. Read once per request with `cache()`.
- **New terms version:** Administrator saves a new version string. `getViewer` sets `mustAcceptTerms` when `User.termsVersion` differs; the platform layout shows a banner "We've updated our terms. Read and accept" linking to `/accept-terms`, which records the version and time.
- **Legal pages** (`/terms-and-conditions`, `/privacy-policy`, `/refund-policy`, `/cookie-policy`) are MDX or TSX pages in `src/app/(public)/`, with the text supplied by Offload.
- **Contact form** (`/contact`): name, email, subject, message (≤ 2,000); honeypot, reCAPTCHA (action `contact`) and rate limit; enqueues an email to `support.email` with the sender's email as reply-to; stores nothing.

## 12. Staff notifications

- Each new pending item (player, manager, organisation, change) calls `notifyStaff(tx, item)`: an in-app notification and an email to every staff member.
- `staff-summary` job (08:00): one email per staff member listing counts still waiting, only when there is at least one.
