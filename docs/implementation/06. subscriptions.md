# 06. Subscriptions and Billing Implementation

How to build `docs/architectural design/06. subscriptions.md` for `docs/requirements/06. subscriptions.md`. Read `01. general_implementation.md` first. Billing mistakes cost real money, so every rule below has a test.

---

## 1. Schema

Add the models from design section 3 with the standard columns: `Plan`, `PlanPrice`, `BillingAccount`, `Subscription`, `Payment`, `Refund`, `DiscountCode`, `DiscountCodePlan`, `WebhookEvent` (id = Stripe event id; `createdAt`, `createdById` only), `BillingReminder` (append-only).

Raw SQL:

```sql
CREATE UNIQUE INDEX sub_one_paid ON "Subscription" ("organisationId") WHERE kind = 'PAID' AND status <> 'ENDED';
CREATE UNIQUE INDEX sub_one_trial ON "Subscription" ("organisationId") WHERE kind = 'TRIAL' AND status <> 'ENDED';
CREATE UNIQUE INDEX discount_code_active ON "DiscountCode" (code) WHERE "isActive";
ALTER TABLE "DiscountCode" ADD CONSTRAINT discount_percent CHECK ("percentOff" BETWEEN 1 AND 100);
ALTER TABLE "DiscountCode" ADD CONSTRAINT discount_code_upper CHECK (code = upper(code));
```

## 2. Stripe client

`src/server/integrations/stripe.ts`:

```ts
export const stripe = new Stripe(env.STRIPE_SECRET_KEY, {
  apiVersion: '<the latest version at implementation time>',  // pinned; the webhook endpoint uses the same version
  maxNetworkRetries: 2,
  appInfo: { name: 'offload' },
})
```

- Every call that creates or changes something passes `{ idempotencyKey }` built from the local ids and action, for example `checkout:${orgId}:${planPriceId}:${minuteBucket}`, `refund:${paymentId}:${amount}:${requestId}`.
- Read the Stripe docs for the pinned version before writing each call. In current versions the subscription's period dates are on the subscription item (`items.data[0].current_period_end`).
- Local development and every rehearsal use **test-mode keys** in `.env.local`. Live keys exist only in `.env.prod`.

## 3. Stripe setup script

`scripts/stripe/setup.ts` (committed). The project owner runs it once per Stripe mode (test, then live): `node --env-file=.env.local --experimental-strip-types scripts/stripe/setup.ts`.

It is safe to run again: everything is found by `lookup_key` or `metadata.offloadKey` first.

1. For each of the 8 plans in requirements section 2: a Product (`metadata.offloadKey = 'club_monthly'`, …) and a GBP Price (`unit_amount` in pence, `recurring.interval` `month` or `year`, `lookup_key` = the same key, `tax_behavior: 'unspecified'`).
2. Customer Portal configuration: payment method update on; customer update on (name, email, address, phone); invoice history on; subscription cancel off; subscription update off; business profile with the Terms and Refund Policy URLs. Prints its id → `STRIPE_PORTAL_CONFIGURATION_ID`.
3. Prints a JSON file `prisma/data/plans.<mode>.json` with the product and price ids, which `prisma/seed.ts` reads to upsert `Plan` and `PlanPrice`.
4. Prints a checklist of dashboard settings to set by hand (the agent asks the owner to do these):
   - Billing → Subscriptions and emails: Smart Retries on, up to 8 attempts within 2 weeks, then **cancel the subscription**
   - Customer emails: all off (successful payments, refunds, failed payments, upcoming renewals, trial reminders)
   - Tax: Stripe Tax off; no tax ids collected
   - Webhook endpoint `https://offloadagency.com/api/stripe/webhook`, API version as pinned, events from section 8; copy its signing secret into `.env.prod`

## 5. Buying

### 5.1 `startCheckout(viewer, planId)`

`src/server/services/billing/checkout.ts`, called from a Server Action that then `redirect(session.url)`:
1. `canBuyPlan` → otherwise return the reason.
2. Transaction: lock the organisation row; create the Stripe Customer if `BillingAccount` is missing (`metadata.organisationId`, `name` = organisation name) and insert `BillingAccount`.
3. Expire open Checkout sessions for this customer (`checkout.sessions.list({ customer, status: 'open' })`, then `expire`).
4. `checkout.sessions.create` with the parameters in design section 5.2, including:
   - `payment_method_collection: 'always'`, `allow_promotion_codes: true`
   - `billing_address_collection: 'required'`, `phone_number_collection: { enabled: true }`, a custom text field `company` (optional)
   - `customer_update: { name: 'auto', address: 'auto' }`
   - `consent_collection: { terms_of_service: 'required' }`, `custom_text.terms_of_service_acceptance` linking Terms and Refund Policy, `custom_text.submit` with the renewal statement
   - during a running staff trial: `subscription_data.trial_end = max(trialEnd, now + 48 hours)` in seconds
   - `success_url: ${APP_URL}/billing/success?session_id={CHECKOUT_SESSION_ID}`, `cancel_url: ${APP_URL}/pricing`

### 5.2 Success page

`/billing/success`: retrieve the session (expanded `subscription`), check it belongs to the viewer's organisation, run `syncSubscription`, then show plan, price, next payment date and "Go to your subscription". If the session is not complete yet, show "Finishing your payment…" and refresh every 2 seconds for up to 20 seconds.

## 6. Sync

`src/server/services/billing/sync.ts`:

- `syncSubscription(stripeSubscriptionId)`:
  1. Retrieve the subscription with `expand: ['items.data.price', 'default_payment_method', 'discounts', 'schedule']`.
  2. Find the local row by `stripeSubscriptionId`, or create it from `metadata.organisationId` (kind `PAID`).
  3. In one transaction with the `BillingAccount` row locked, write status (design section 3 mapping, except keep `PAUSED` while `pause_collection` is set), plan and price (from the Price id), period dates, `isCancelledAtPeriodEnd`, discount, schedule fields, `pastDueSince` (set on the first move to `PAST_DUE`, cleared otherwise), `accessEndedAt`/`endedReason` when it ends.
  4. Compare old and new values and enqueue the emails from design section 10 for real changes only.
- `syncInvoice(invoiceId)`: upsert `Payment` by `stripeInvoiceId` (amounts, status, attempts, last failure message, period, paid date).
- `syncCustomer(customerId)`: update `BillingAccount` name, company, email, phone, address and card brand and last 4 from the default payment method.

## 7. Lifecycle services

`src/server/services/billing/lifecycle.ts`. Each one checks the policy, locks the `BillingAccount`, calls Stripe, then updates the local rows and writes a `billing.*` audit event in one transaction.

| Function | Stripe | Local |
|---|---|---|
| `cancelAtPeriodEnd(viewer)` | release schedule if any; `subscriptions.update(id, { cancel_at_period_end: true })` | `isCancelledAtPeriodEnd`, clear `scheduledPlanId`; email |
| `undoCancel(viewer)` | `cancel_at_period_end: false` | email |
| `schedulePlanSwitch(viewer, planId)` | `subscriptionSchedules.create({ from_subscription })`, then `update` with two phases (current price until period end, new price after), `end_behavior: 'release'`, `proration_behavior: 'none'` | `scheduledPlanId`, `stripeScheduleId` |
| `cancelPlanSwitch(viewer)` | `subscriptionSchedules.release` | clear both |
| `pauseForOrganisation(tx, orgId)` | `pause_collection: { behavior: 'void' }`; release schedule | `PAUSED`, `pausedAt`, `pausedRemainingSeconds`; trials: local only |
| `resumeForOrganisation(tx, orgId)` | remaining > 0: `trial_end = now + remaining`, `proration_behavior: 'none'`, `pause_collection: ''`; remaining 0: `pause_collection: ''`, `billing_cycle_anchor: 'now'` | re-create a kept plan switch; sync |

`pauseForOrganisation` and `resumeForOrganisation` are called by the `03` lifecycle services inside their transaction; the Stripe call happens before commit, and a failure throws so the unpublish or republish is refused.

## 8. Webhook

`src/app/api/stripe/webhook/route.ts`:

```ts
export async function POST(request: Request) {
  const body = await request.text()
  const signature = request.headers.get('stripe-signature')
  if (!signature) return new Response('missing signature', { status: 400 })
  let event: Stripe.Event
  try {
    event = stripe.webhooks.constructEvent(body, signature, env.STRIPE_WEBHOOK_SECRET)
  } catch {
    return new Response('invalid signature', { status: 400 })
  }
  return runAsSystem(() => handleStripeEvent(event))   // 200, or 500 so Stripe retries
}
```

`handleStripeEvent` (`src/server/services/billing/webhook.ts`):
1. `INSERT INTO "WebhookEvent" (id, type) … ON CONFLICT (id) DO NOTHING`. If the existing row has `processedAt`, return 200.
2. Route by type:

| Event | Handler |
|---|---|
| `checkout.session.completed` | `syncSubscription(session.subscription)`; double-purchase check (design 5.2); discount usage |
| `customer.subscription.created`, `.updated`, `.deleted` | `syncSubscription(id)` |
| `invoice.paid`, `invoice.payment_failed`, `invoice.payment_action_required` | `syncInvoice(id)` then `syncSubscription(subscription id)` |
| `charge.refunded`, `refund.updated` | upsert `Refund`, update `amountRefundedPence`, refund email |
| `customer.updated`, `payment_method.attached` | `syncCustomer` |
| `subscription_schedule.released`, `.canceled` | clear matching schedule fields |
| anything else | ignored (return 200) |

3. Set `processedAt`. On error store `error`, return 500. A failure that repeats 3 times alerts staff.
4. Refresh caches with `revalidateTag` (never `updateTag` here).

Exclude `/api/stripe/webhook` from `proxy.ts` and from the CSRF/origin checks.

## 9. Manager pages

- `/pricing` (public, `'use cache'` with tag `plans`): plans grouped by organisation type with a monthly/annual switch (client component); each "Subscribe" button's state comes from `canBuyPlan`, rendered in a per-viewer `<Suspense>` part.
- `/dashboard/subscription` (`canManageBilling`): the fields in design section 6.1 from local tables; buttons for Update payment method and Update billing details (Server Action → `billingPortal.sessions.create({ customer, configuration, return_url })` → redirect), Cancel, Undo cancellation, Switch plan, Cancel switch.
- `/billing/invoices/[paymentId]`: check the organisation, `invoices.retrieve`, redirect to `invoice_pdf`.
- Past-due banner in the platform layout for managers of an organisation with `PAST_DUE` past the grace period: "Your payment failed. Update payment method".

## 10. Discount codes

`src/server/services/billing/discounts.ts`:
- `createDiscountCode({ code, percentOff, planIds, duration, durationMonths, expiresAt, maxRedemptions })`: upper-case the code; `coupons.create({ percent_off, duration, duration_in_months, applies_to: { products } })`; `promotionCodes.create({ coupon, code, expires_at, max_redemptions })`; insert the rows.
- `changeLimits(id, …)`: deactivate the old promotion code, create a new one with the same code and `max_redemptions = max − used`, update the row.
- `expire(id)`: `promotionCodes.update(id, { active: false })`, `isActive = false`.
- `applyToSubscription(subscriptionId, discountCodeId)` (staff): `subscriptions.update(id, { discounts: [{ coupon }] })`.

## 12. Jobs

| Job | Implementation |
|---|---|
| `billing` (09:00) | End trials past `currentPeriodEnd`; handle grace ends (`accessEndedAt`, "access stopped" email once); send reminders (design section 5.7). Each reminder inserts `BillingReminder (subscriptionId, kind)` with `ON CONFLICT DO NOTHING` and sends only when the insert happened. |
| `billing-reconciliation` (04:00) | `syncSubscription` for every local `PAID` not `ENDED`, and for every Stripe subscription with `created` or updates in the last 2 days (`subscriptions.list` with auto-paging); re-run failed `WebhookEvent` rows; report differences to staff |
| `billing-retention` (1 January) | Delete billing rows whose last payment is older than 6 years, then `customers.del` |

## 13. Emails

Email types (template ids in `src/server/email/types.ts`): `billing.subscription-started`, `billing.trial-started`, `billing.receipt`, `billing.trial-ending`, `billing.renewal-near`, `billing.payment-failed`, `billing.payment-recovered`, `billing.access-stopped`, `billing.cancelled`, `billing.paused`, `billing.resumed`, `billing.ended`, `billing.subscribe-again`, `billing.refund`, `billing.plan-changed`. ## 14. Testing

- Fixtures: real Stripe test-mode event JSON saved in `tests/fixtures/stripe/` (remove customer emails and names first, keep ids fake).
- Integration tests feed fixtures to `handleStripeEvent` with the Stripe client mocked for `retrieve` calls; check repeated and out-of-order events give the same final state and send each email once.
- Manual end-to-end in test mode with **test clocks**: subscribe → players directory opens → advance to renewal with a failing card → access during grace → access stops after 7 days → update the card → access returns; also cancel, undo, plan switch at period end, pause and resume.
